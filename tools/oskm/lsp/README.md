# 在 OpenCode 中使用 LSP

这份指南介绍如何使用已准备好的 LSP 环境进行 C/C++ 代码查询和分析。

日常使用分三步：**在源码根目录打开 OpenCode，等待索引加载，然后在对话框中描述要查询的问题。**

## 使用前检查 bwrap（一般已安装）

CodeSpace 环境一般已经安装 bwrap（软件包名为 `bubblewrap`），已安装时可以直接继续，无需重复安装。LSP 的可迁移索引通过 bwrap 保持流水线和当前工作区的路径视图一致。

先在终端检查：

```bash
command -v bwrap
```

如果输出 bwrap 的可执行文件路径，说明已经安装。只有未找到命令时，才需要在 Ubuntu / Debian 环境中使用 sudo 安装：

```bash
sudo apt update && sudo apt install -y bubblewrap
```

安装完成后确认命令可用：

```bash
bwrap --version
```

如果没有 sudo 权限，请联系环境提供方安装。确认可用后，按下面的步骤从源码根目录启动 OpenCode。

## 1. 在源码根目录启动 OpenCode

打开终端，进入 OpenHarmony 源码根目录，再启动 OpenCode：

```bash
cd /path/to/openharmony
opencode
```

将 `/path/to/openharmony` 替换为自己的源码根目录。这个目录下应能看到 `.repo/`、`base/`、`foundation/`、`out/` 等目录。

每次都从这个目录启动，不要进入 `tools/oskm/lsp/` 后再启动。

## 2. 等待索引加载到内存

已配置自动预热的环境中，打开 OpenCode 后，LSP 会自动启动并开始加载索引。先等待数分钟，再查询跨文件引用和调用关系。实际等待时间取决于索引大小、磁盘和机器负载。

加载期间保持窗口打开，避免反复退出重开。

等待后，在 **OpenCode 对话框** 中输入：

```text
请用 lsp 检查当前 C/C++ 语言服务是否正常运行，
并告诉我它对应的是哪个源码根目录。
```

确认服务正常、源码目录正确后，可以试一次查询：

```text
请用 lsp 查找 ServiceWatchForStatus 的定义，
再查找其他文件中对它的引用，列出文件路径和行号。
```

可以将示例函数换成自己熟悉、当前产品中包含的函数。如果服务正常运行但跨文件结果暂时不完整，继续等待一会儿再查。服务启动成功不等于所有索引都已加载，当前接口也没有全量加载完成百分比。

若服务尚未启动，可以先让 OpenCode 查询一个具体文件：

```text
请用 lsp 列出下面文件中的函数：
/path/to/openharmony/base/startup/init/interfaces/innerkits/service_watcher/service_watcher.c
```

将路径前缀替换为自己的源码根目录。查询文件会按配置自动启动语言服务，首次查询可能需要等待。

## 3. 在对话框中直接描述任务

下面的示例都直接输入 **OpenCode 对话框**。把函数名、类名或文件路径替换成自己要分析的对象即可，工具参数由 OpenCode 自动填写。

建议在提问中包含“请用 lsp”，并要求附上文件路径和行号。如果只做分析，可以加上“只查询，不修改代码”。

### 查函数、类或变量在哪里定义

```text
请用 lsp 查找 ServiceWatchForStatus 的定义，
告诉我它在哪个文件、第几行，并说明函数参数和返回值。
```

有多个同名符号时，补充所属文件、类或命名空间：

```text
请用 lsp 查找 service_watcher.c 中的 ServiceWatchForStatus，
只分析这个文件中的同名函数。
```

### 查谁调用了这个函数

```text
请用 lsp 查找哪些函数直接调用了 ServiceWatchForStatus，
按“调用者 → ServiceWatchForStatus”列出关系，附上调用位置。
```

### 查这个函数调用了哪些函数

```text
请用 lsp 分析 ServiceWatchForStatus 直接调用了哪些函数，
按“ServiceWatchForStatus → 被调用函数”列出关系，附上调用位置。
```

### 继续向上或向下追踪调用链

```text
请用 lsp 从 ServiceWatchForStatus 开始，向下追踪两层调用关系。
逐层查询，列出调用链和代码位置；重复节点不重复展开，遇到环路停止。
```

查入口时，可以改成“向上追踪两层调用关系”。追踪深度写清楚，便于控制结果规模。

### 查函数或变量在哪些地方使用

```text
请用 lsp 查找 ServiceWatchForStatus 的所有引用，
按文件分组列出位置。如果结果分批返回，请继续查询剩余结果。
```

引用还可能包含取函数地址等用法。若只关心函数调用，请直接说“查直接调用者”。

### 看文件结构

```text
请用 lsp 列出下面文件中的函数、类和成员，
先给出结构概览，再说明主要函数的作用：
<源码文件的绝对路径>
```

将占位内容替换为实际文件路径。完整路径可以减少同名文件造成的歧义。

### 看类型、实现和继承关系

```text
请用 lsp 查看这个变量的类型，并跳转到它的类型定义。
```

```text
请用 lsp 查找这个虚方法有哪些实现，列出实现所在的文件和行号。
```

```text
请用 lsp 查看这个类的父类和子类，列出继承关系。
```

这里的“这个变量”“这个类”应是对话中已经定位的对象。首次提问时，请补上名称和所属文件。

### 检查修改后的错误和警告

```text
请用 lsp 检查我刚修改的这个文件，列出错误和警告的位置及原因。
只检查，不自动修复。
```

检查多个文件时：

```text
请用 lsp 打开并检查我刚修改的这些文件，汇总错误和警告，
并说明实际检查了哪些文件。
```

工作区诊断只汇总已打开文件的诊断，不会自动检查整个源码树。LSP 检查后，仍需进行相应编译或测试。

### 重命名、修复和格式化

需要修改代码时，先要求展示预览：

```text
请用 lsp 将这个函数重命名为 <新名称>。
先展示涉及哪些文件、哪些位置，暂不应用修改。
```

```text
请用 lsp 查看这个报错位置有哪些快速修复建议，
先列出建议，不应用修改。
```

```text
请用 lsp 预览这个文件的格式化结果，暂不写入文件。
```

检查预览后，可以继续说“应用刚才预览的重命名”或“应用第一个修复建议”。应用后检查代码差异，并运行对应编译或测试。

## 4. LSP 提供了哪些接口

日常提问可以只描述任务。需要明确指定工具时，在对话中写“请调用 `lsp_find_symbol` 查找……”即可。工具名用于对照 OpenCode 的调用记录。

### 查符号、定义和调用关系

| 接口 | 能做什么 |
| --- | --- |
| `lsp_find_symbol` | 按名称定位函数、类、变量等符号 |
| `lsp_workspace_symbols` | 搜索工作区中的符号，查看多个匹配项 |
| `lsp_goto_definition` | 跳转到符号定义 |
| `lsp_goto_type_definition` | 跳转到符号的类型定义 |
| `lsp_find_references` | 查找符号的引用位置 |
| `lsp_find_implementations` | 查找接口或虚方法的实现 |
| `lsp_hover` | 查看类型、函数签名和说明 |
| `lsp_signature_help` | 查看函数调用的参数提示 |
| `lsp_smart_search` | 一次组合查询定义、类型、引用、调用关系等信息 |
| `lsp_call_hierarchy` | 查询函数的直接调用者、直接被调用函数 |
| `lsp_type_hierarchy` | 查询类型的父类和子类关系 |

### 看文件结构和局部信息

| 接口 | 能做什么 |
| --- | --- |
| `lsp_document_symbols` | 查看文件中的函数、类、成员等结构 |
| `lsp_file_exports` | 查看顶层符号及签名；不等同于 C/C++ 的对外导出接口 |
| `lsp_file_imports` | 查看 import / require 形式的导入，主要适用于 JS/TS，不用于查询 C/C++ 头文件包含关系 |
| `lsp_related_files` | 查看导入与被导入关系，主要适用于 JS/TS；反向查询范围限已打开文件 |
| `lsp_document_highlights` | 查看同一符号在当前文件中的出现位置 |
| `lsp_inlay_hints` | 查看类型或参数名提示 |
| `lsp_selection_range` | 查看当前位置所属的表达式、语句或代码块范围 |
| `lsp_folding_ranges` | 查看文件中可折叠的代码区域 |

### 检查代码和辅助修改

| 接口 | 能做什么 |
| --- | --- |
| `lsp_diagnostics` | 查看一个文件的错误、警告和提示 |
| `lsp_workspace_diagnostics` | 汇总已打开文件的诊断 |
| `lsp_index_files` | 批量打开或刷新指定文件，供诊断等查询使用 |
| `lsp_completions` | 获取当前位置的代码补全建议 |
| `lsp_rename` | 预览或应用符号重命名 |
| `lsp_code_actions` | 查看或应用快速修复、重构建议 |
| `lsp_format_document` | 预览或应用文件格式化 |

### 查看和管理服务

| 接口 | 能做什么 |
| --- | --- |
| `lsp_server_status` | 查看语言服务是否运行、对应源码目录和支持的能力 |
| `lsp_start_server` | 手动启动语言服务，通常无需单独操作 |
| `lsp_stop_server` | 停止语言服务并释放资源 |

共 29 个接口。具体操作能否使用，以当前语言服务的支持情况和实际返回结果为准。

## 5. 同时打开多个 OpenCode 窗口

同一用户在同一源码根目录、使用相同 LSP 配置和安装位置时，多个 OpenCode 窗口会自动共用后台和已加载的内存索引。

第二个窗口仍然这样启动：

```bash
cd /path/to/openharmony
opencode
```

关闭其中一个窗口，其他窗口可以继续使用。所有窗口退出后，后台默认再保留 5 分钟；若后台已退出，下次打开时需重新等待索引加载。

多个窗口使用同一份磁盘文件，修改后先保存再查询。另一个窗口正在执行较慢的查询时，当前窗口的请求可能需要排队。

## 6. 查询不正常时怎么处理

### OpenCode 没有调用 LSP

在对话框中补充：

```text
请实际调用 lsp 工具后再回答，列出使用的工具和返回的代码位置。
```

若仍提示没有工具，在另一个终端从源码根目录检查连接：

```bash
cd /path/to/openharmony
opencode mcp list
```

确认列表中有 `lsp` 且连接正常。没有发现服务或连接报错时，将错误信息交给环境提供方检查。

### 查询为空或结果不完整

先等待一会儿，再重试。随后补充文件路径，确认查找的是正确符号。

```text
请在我指定的文件中重新定位这个函数，再查询引用和调用关系。
如果结果分批返回，请继续取完；如果某项查询不支持或失败，请明确说明。
```

当前产品未编译的代码可能不在索引覆盖范围内。函数指针、回调注册、IPC 和运行时分发等间接关系，也不保证出现在静态调用链中。

### 修改文件后仍显示旧结果

先保存文件，再在对话框中输入：

```text
请用 lsp 重新读取这个文件，并重新定位目标符号、检查诊断。
```

### 查询超时或服务启动失败

避免反复重开窗口。保留完整报错，交给环境提供方检查服务、索引和运行环境。

若提示服务正被其他客户端共享，日常查询可以继续使用；需要停止服务时，先协调其他窗口退出。
