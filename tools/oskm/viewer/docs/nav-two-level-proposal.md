# 二级菜单改造方案

日期：2026-10-19
版本：1.1
状态：**已实施**，实施记录见 §9。

针对：一级菜单支持二级，分为 运行时进程（系统服务 / SA服务 / HDI服务）、
部件信息（代码仓 / 部件）、系统文件（安装目标 / 镜像视图）。

## 1. 我的理解

七个二级项对应的数据与现状：

| 菜单 | 数据来源 | 行数 | 现状 |
| --- | --- | ---: | --- |
| 1.1 系统服务 | `services` | **164** | 已有，就是现在的"运行视图"表格 |
| 1.2 SA服务 | `sas` | **165** | **新建**。目前只能从运行单元或抽屉里零散看到 |
| 1.3 HDI服务 | `hdis` | **57** | **新建**，同上 |
| 2.1 代码仓 | `repos` | **525** | **新建**（产品面）。目前只在调测面 `/data/repos` |
| 2.2 部件 | `components` | **382** | 已有，就是现在的"构建视图"卡片网格 |
| 3.1 安装目标 | `install_targets` | **5804** | **新建** |
| 3.2 镜像视图 | `install_targets` | 5804 | 已有，路径树 |

这个结构把**现在够不着的东西露出来了**：SA 和 HDI 今天在产品面没有自己的列表，
想回答"全系统 165 个 SA 哪些是 run-on-create"只能去调测面翻原始表。
代码仓同理。这三个是实打实的补缺，不是换个地方摆。

数据侧已验证可行：165/165 条 SA 都能关联到宿主进程，HDI、安装目标的关联链也完整。

## 2. 一个硬约束：el-table 撑不到 5804 行

这是整个方案里唯一真正的障碍，而且是实测的，不是估计。
把运行视图的表格按行数放大，同一套代码：

| 行数 | 首屏 | 重渲染全集 |
| ---: | ---: | ---: |
| 164（系统服务 / SA服务） | 2.7 s | 0.55 s |
| 492（≈ 代码仓 525） | 4.0 s | 1.35 s |
| **5904（≈ 安装目标 5804）** | **33 s** | **14 s** |

**安装目标按现在这套做法直接不可用。** 代码仓 525 行也已经到了难受的边缘。

上一轮已经逐项验证过这不是我们渲染的问题：把整个单元格模板塌成一个纯插值
仍要 420 ms / 164 行，开销在 el-table 自身的每行机制里。

### 2.1 解法：分页

`el-pagination` + el-table，调测面 `/data/*` 已经在用，成熟、零新轮子。
关键是分的只是**渲染**：排序、筛选、搜索、导出仍然在全量数据上做
（5804 行的数组操作是毫秒级的），所以"翻页会不会把数据切碎"这个担心不成立。

建议：**所有列表统一挂分页条**，每页 50 / 100 / 200 / 全部 可选，默认 100，页大小进 URL。

- 统一比"超过 N 行才分页"好：行为可预期，不会出现"这个表能 Ctrl-F 那个不能"
- 保留"全部"选项：真要 Ctrl-F 全表时自己选，并自行承担 5804 行的等待
- 顺带把系统服务的筛选切换从 420 ms 压回 ~250 ms

代价：默认视图下 Ctrl-F 只覆盖当前页。补偿是搜索框已经覆盖全量所有可见列。

> 另一条路是 `el-table-v2` 虚拟滚动。它对**安装目标**其实很合适（叶子表，
> 不需要展开行），但 API 与 el-table 完全不同（列用 JS 数组 + `cellRenderer`
> 写 VNode），等于在同一个产品里维护两套表格写法。除非分页实测不可接受，
> 否则不建议。

## 3. 二级菜单做成什么形态

### 甲：顶栏下拉二级菜单

点一级 → 浮出二级列表。

- 省空间，和现在的"数据▾"一致
- 但：子项不可见，得先点开才知道有什么；而且**这是刚修过 bug 的那类交互**
  （下拉菜单的指针进出，见 `implementation-plan` §14.10）。再加三个下拉，
  就是三份同样的风险面

### 乙：常驻子导航条（推荐）

顶栏放一级，下面一条细条显示**当前一级组的全部子项**：

```
┌───────────────────────────────────────────────────────────────────┐
│ oskm   首页 │ 运行时进程 │ 部件信息 │ 系统文件     [反查] 质量 数据▾│
├───────────────────────────────────────────────────────────────────┤
│        系统服务 164 · SA服务 165 · HDI服务 57                      │
└───────────────────────────────────────────────────────────────────┘
```

- **子项常驻可见**，不点开就知道同组还有什么、各有多少条
- **零下拉交互**，不新增悬停/点击的风险面
- 点一级 → 直接去该组第一个子项（一次点击到位，不是两次）
- 当前位置在两层上同时高亮，"我在哪"一眼可见
- 代价：固定占 36 px 高度。首页与档案页可以不显示这条

### 丙：左侧两级树

- 层级最清楚，适合十几个以上的叶子
- 但七个叶子撑不起一整条侧栏，而且会占掉 200 px 横向宽度——
  安装目标这种 19 列的宽表最吃横向空间

**推荐乙。** 七个叶子、三个分组，正好是子导航条最舒服的规模；
而且它把"每组有多少条"这个信息顺手给了出来。

## 4. URL 与一个路由冲突

```
#/runtime            → 重定向到 #/runtime/services
#/runtime/services   1.1 系统服务
#/runtime/sa         1.2 SA服务
#/runtime/hdi        1.3 HDI服务
#/runtime/unit/:id   运行单元档案（原 #/runtime/:id）

#/parts              → 重定向到 #/parts/components
#/parts/repos        2.1 代码仓
#/parts/components   2.2 部件

#/files              → 重定向到 #/files/image
#/files/targets      3.1 安装目标
#/files/image        3.2 镜像视图
```

**冲突**：现有的 `#/runtime/:id`（运行单元档案）会把 `#/runtime/sa` 当成 id=sa 吃掉。
所以档案页要挪到 `#/runtime/unit/:id`。旧地址加重定向，`tools/nav.mjs` 里的断言同步改。

其余不变：`#/`、`#/lookup`、`#/findings`、`#/e/<table>/<id>`、`#/data/*`，
以及全局的 `?scan=` 与 `?detail=`。每个列表各自的
`sort` / `dir` / `hide` / `page` / `size` / 筛选参数沿用现有规矩（`url-spec` §1）。

## 5. 架构：不要写七遍表格

现在的 `Runtime.vue` 是 382 行，里面混着两类东西：

- **通用的**：排序、筛选、搜索、列显隐、分页、导出、带 ⓘ 的表头、三态渲染
- **专属的**：19 列的目录、一句话的混装提示、展开行的内容

七个视图里有六个要表格。照抄六遍是 2000 多行重复，改一个 bug 要改六处。

所以第一步是把通用部分抽成 `components/EntityTable.vue`（约 320 行），
每个视图只提供三样：

```js
// views/SaList.vue 大致长这样，约 40 行
const rows = ref([])
watch(() => store.scanId, id => { rows.value = loadSas(id) }, { immediate: true })
<EntityTable :rows="rows" :columns="SA_COLUMNS" :facets="SA_FACETS"
             @open="r => openEntity(router, route, 'sas', r.id)" />
```

列目录按视图分文件：`model/fields/services.js`、`sas.js`、`hdis.js`、
`repos.js`、`components.js`、`targets.js`。每个 60–120 行，
沿用上一轮定下的写法：人话列名 + 含义（通用约定）+ 在 oskm 里怎么来的 + 实时分布。

**一个必须守住的点**：SA / HDI 的"宿主进程"要经 `service_id → services.name` 关联取，
**不能读 `sas.process` / `hdis.process`**——扫描器当前 schema 里已经没有这两列了
（本地 `knowledge.db` 是旧的，还留着，照着它写会做出一个新库打不开的视图）。
这个坑踩过一次。

## 6. 三件需要你定（已回复）

> 6.1 → `install_modules` **并入 3.1 安装目标**，一行一个文件、同时展示模块信息，1:N 由列与展开行体现
> 6.2 → **统一用表格**，不用卡片
> 6.3 → 确认，设计文档随之改写


### 6.1 安装模块（`install_modules`，5501 行）没有入口

它是归属判定的枢纽（5 条外键指向它），现在产品面只能从别处顺带点进去。
新结构里没给它位置。三个选择：

- **放进"系统文件"做 3.3**（安装模块 → 安装目标是一对多，和这组很搭）
- 放进"部件信息"做 2.3（它归属于部件）
- 不给入口，维持现状

### 6.2 "部件"（2.2）要不要从卡片改成表格

现在是卡片网格 + 子系统分面。改成表格才和其它六个一致，
而且 382 行能排序/导出。但部件卡片上的"被 N 个部件依赖"这种信息，
表格里是一列，视觉重量会降。建议改表格、保留子系统分面条。

### 6.3 旧的"构建视图 / 镜像视图"这两个名字

新结构里，"构建"这个一级入口消失了（拆成 2.2 部件 + 2.1 代码仓），
"镜像"降为 3.2。`ux-design.md` 的四视角叙事（运行 / 构建 / 镜像 + 反查）
要跟着改写成三组七视图。确认后我一并更新设计文档。

## 7. 分期

| 步 | 内容 | 量 |
| --- | --- | --- |
| **一** | `EntityTable.vue` 抽取 + 分页；`Runtime.vue` 改为它的使用者（行为不变，但有了分页） | ~420 行，净减 |
| **二** | 子导航条 + 路由重构（含 `/runtime/unit/:id` 迁移与旧址重定向） | ~180 行 |
| **三** | 新建 SA服务 / HDI服务 / 代码仓 / 安装目标 四个视图 + 四份列目录 | ~400 行 |
| **四** | 部件改表格（若 6.2 确认）；设计文档与 `url-spec` 同步 | ~150 行 |

每步独立可验收。回归：`tools/table.mjs` 参数化成"对每个列表视图跑同一组断言"
（排序含三态、筛选进 URL、分页进 URL、导出与屏幕一致、ⓘ 有三段内容），
再加一组菜单断言（两级高亮、一级点击直达默认子项、子项计数正确）。

性能上要新立的预算：**每个列表视图首屏 ≤ 3 s、翻页 ≤ 300 ms、筛选切换 ≤ 600 ms**，
在默认每页 100 行的前提下。安装目标选"全部"时不设预算，但界面要给出提示。

## 9. 实施记录（2026-10-19）

### 9.1 结构落地

七个二级视图全部就位，一级三组 + 首页，二级为常驻子导航条（方案乙）。

| 菜单 | 路由 | 行数 | 默认列 |
| --- | --- | ---: | ---: |
| 1.1 系统服务 | `/runtime/services` | 164 | 9 / 19 |
| 1.2 SA服务 | `/runtime/sa` | 165 | 5 / 11 |
| 1.3 HDI服务 | `/runtime/hdi` | 57 | 4 / 12 |
| 2.1 代码仓 | `/parts/repos` | 525 | 5 / 9 |
| 2.2 部件 | `/parts/components` | 382 | 6 / 14 |
| 3.1 安装目标 | `/files/targets` | 5804 | 6 / 13 |
| 3.2 镜像视图 | `/files/image` | 树形 | — |

运行单元档案从 `/runtime/:id` 挪到 `/runtime/unit/:id`——原路由会把 `/runtime/sa`
当成 id 吃掉。`/runtime`、`/build`、`/image` 都加了重定向，旧链接不失效。

### 9.2 `install_modules` 并入安装目标

一行 = 一个装进镜像的文件，同时带上装出它的模块（label / 类型 / 构建产物 /
是否参与安装 / 清单序号）。1:N 用两处体现：「同模块文件」列（1 / 2 / 3），
以及展开行列出同模块的其它文件并标出当前这一行。

之所以以**目标**为行而不是以模块为行：实测 5501 个模块装出 5804 个文件，
**95% 的模块只装 1 个、最多 3 个**。以模块为行要多一次展开才能看到路径，
而路径恰恰是最常用来搜索和定位的东西。

### 9.3 分页：从 33 秒到 2.5 秒

`EntityTable` 统一挂分页条，默认 100 条/页，可选 50/100/200/500 与「显示全部」。
**分的只是渲染**——排序、搜索、导出都在全量上做，所以导出按钮上的数字始终是
整个筛选结果的行数，不是当前页。

| | 改前 | 改后 |
| --- | ---: | ---: |
| 安装目标 5804 行首屏 | 33 s | **2.5 s** |
| 代码仓 525 行首屏 | ~4 s | 1.1 s |
| 系统服务切换筛选 | 420 ms | 237 ms |

`tools/perf.mjs` 的筛选预算因此从 600 ms **收回到 400 ms**（上一轮为了 el-table
放宽到 600，现在分页把它赚回来了一部分）。

### 9.4 EntityTable：六个视图一套代码

`Runtime.vue` 从 382 行缩到 113 行；新增的五个视图各 48–98 行，
列目录 36–133 行。通用部分（搜索 / 排序 / 分页 / 列显隐 / 导出 / ⓘ 表头 /
三态渲染 / 超量内容）在 `EntityTable.vue` 一处。

回归也跟着收敛：`tools/table.mjs` 对六个视图跑同一组断言
（有数据、列名是人话、有分页条、每列有 ⓘ），一处断言覆盖六个视图。

### 9.5 超量内容

单元格文本超过阈值（默认 90 字符，列可单独设 `full`）时，显示截断 + `⤢`，
点开是可滚动、可选中复制的全文。实测最长：`record` 14489 字符、
`components.deps` 1140、`install_modules.label` 159、`install_targets.dest` 108。

`record` 本身不进任何列表，只在运行单元详情页的「其它声明」里展开。

### 9.6 实施中查出来的

- **差点覆盖掉调测面的视图。** `src/views/RepoList.vue` 已经存在（`/data/repos` 的
  7 行壳子），我按同名新建就把它盖了。产品面列表统一挪到 `src/views/list/` 下，
  与调测面彻底分开。
- **el-pagination 的文案是英文。** "Total / 100/page / Go to"——按需导入模式下
  装不了整包 locale，用 `ElConfigProvider` 注入 `zh-cn`，调测面一并受益。
- **分页器当前页码 2.51:1**（`tools/a11y.mjs` 抓出）。Element Plus 在
  `--el-color-primary` 底上一律放白字，而我们的主色是浅蓝。
  **不要跟它比选择器优先级**——按需导入的组件 CSS 总是后加载，同优先级下它赢；
  改写 `--el-color-white` 变量让它自己的规则取到我们的 `--text-inverse`。
- **至少要有两列默认可见且用 `min`。** 一列都没有则右边留空白，
  只有一列则它把剩余宽度全吃掉（SA 视图的"实现库"一度宽到离谱）。
- **列表视图的滚动容器换了。** 从视图自己的 `overflow:auto` 变成 el-table 内部的
  `.el-scrollbar__wrap`，滚动记忆要重新挂上去，否则每次返回都回到顶部。
