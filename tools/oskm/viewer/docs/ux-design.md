## 1. 目标与读者

**目标**：让人在不懂数据库 schema 的前提下，看懂一个 OpenHarmony 产品"由什么构成、装了什么、跑起来是什么样"。

| 读者 | 典型任务 | 对 UI 的要求 |
| --- | --- | --- |
| **系统开发者** | 我要改 X 部件：它对外提供什么、谁依赖它、运行时体现在哪 | 从**一个名字**出发看全貌 + 依赖邻域 |
| **测试 / 集成** | 崩在 `libfoo.z.so` 里，这是谁的？这东西装进去了吗？ | 从**一条现场线索**反查归属 |
| （次要）**oskm 开发者** | 这次扫描采到了什么、对不对、哪张表有问题 | 原始表 + SQL + 扫描元信息 |

前两类的交集是**归属链**（仓 → 部件 → 模块 → 安装路径 → 运行形态），
分歧在**入口方向**：开发者从名字进，测试集成从路径 / 进程 / so 名进。两个入口都必须有。

## 2. 导航结构：三组七视图

一级是概念分组，二级是具体视图；二级做成**常驻子导航条**而不是下拉——
子项常驻可见、点一级一次到位、不新增悬停/点击的风险面。
详见 `nav-two-level-proposal.md`。

```
oskm   首页 │ 运行时进程 │ 部件信息 │ 系统文件      [反查 ⌘K] 质量 数据▾ ☾ rk3568#1▾
       系统服务 164 · SA 服务 165 · HDI 服务 57
```

| 一级 | 二级 | 回答什么问题 | 行数 |
| --- | --- | --- | ---: |
| **运行时进程** | 系统服务 | 这个进程里跑着什么、是谁的代码 | 164 |
| | SA 服务 | 全系统有哪些 SA、各自跑在哪个进程里 | 165 |
| | HDI 服务 | 有哪些设备驱动、宿主是谁、归属哪个部件 | 57 |
| **部件信息** | 部件 | 这个部件产出了什么、被谁依赖 | 382 |
| | 代码仓 | 代码在哪、哪些仓真的参与了构建 | 525 |
| **系统文件** | 安装目标 | 镜像里这个文件是谁装的、属于哪个部件 | 5804 |
| | 镜像视图 | 这个目录里装了什么（按路径浏览） | 树形 |

次级入口（不属于任何一组，常驻顶栏右侧）：

- **反查**（⌘K）：给一条线索（路径 / so 名 / 进程名 / label），反查归属
- **质量**：当前扫描暴露的不一致，过程性的，会随治理收敛
- **数据**：调测面 `/data/*`，原始表格，面向 oskm 自身开发与数据核对

六个列表视图共用 `EntityTable`：任意列排序、搜索、列显隐、分页、导出、
表头 ⓘ 字段说明、三态渲染、超量内容展开。状态全部进 URL（见 `url-spec.md`）。

## 4. 运行视图（第一个实现）

### 4.1 建模：运行单元 = 一条 service 声明

库里没有"进程"表，但 `services.id` 已被 `sas.service_id` / `hdis.service_id` 引用——
**一条 service 声明就是一个运行单元**，内容由外键给出。不另造实体、不另建表。

| 类型 | 条数 | 内容来自 | 含义 |
| --- | ---: | --- | --- |
| `sa` | 104 | `sas.service_id` | sa_main 拉起的 SA 宿主进程 |
| `hdf` | 28 | `hdis.service_id` | hdf_devhost 拉起的驱动宿主 |
| `default` | 31 | 无 | 普通守护进程（hdcd / appspawn / bootanimation …），30/31 有归属 |
| 未分类 | 1 | — | `path` 缺失，无法判定 |

### 4.2 首屏：表格

```

其中 13 个装载了多个部件的内容——改动影响面与崩溃定位都卡在这里。   ← 可点，一键只看这 13 个
[全部 164][SA 宿主 104][驱动宿主 28][守护进程 31]  [搜索][按部件▾][按子系统▾][列 9/19▾][导出 164 行▾]
┌──┬──────────────┬────────┬──────────────────┬──────────┬──────┬──────┬────┬────┬──────────┐
│▸ │ 进程名 ⓘ⇅    │ 类型 ⓘ⇅│ 启动配置 ⓘ⇅      │归属部件ⓘ⇅│装载⇅ │涉及⇅ │混装│问题│运行用户⇅ │
├──┼──────────────┼────────┼──────────────────┼──────────┼──────┼──────┼────┼────┼──────────┤

│  │   └ 装载 11 项 · 来自 1 个部件：usb_host_driver · …                                     │
```

**为什么是表格不是卡片**：164 个同构对象、十几个属性、要横向比较——
卡片适合"少量对象各讲一个故事"，这里是"找出哪一个不一样"。
一张卡片装得下 6 个事实，一行能摊 18 个。详见 `runtime-table-assessment.md`。

四件事：

- **任意列排序**。三态列（沙箱 / 按需启动 / 重要级）的"未声明"**恒定排末尾**，
  升序降序都一样——否则降序时先看到的是一百多行空白。
- **列显隐**，19 列默认显示 9 列，按"身份 / 归属 / 装载 / 运行身份与安全"分组。
- **搜索覆盖所有可见列**，不只是名字。
- **导出 CSV / JSON**：当前筛选 × 当前可见列 × 当前排序，与屏幕完全一致；
  文件名带上筛选条件。

筛选、排序、列显隐**全部进 URL**，与 `url-spec.md` §1 一致。

### 4.2.1 每列都要能被看懂

列名用人话（`secon` → "SELinux 上下文"、`uid` → "运行用户"），
表头的 ⓘ 点开是三段说明：

- **含义** —— init / 构建体系的通用约定
- **在 oskm 里怎么来的** —— 这一列怎么算出来的、有什么坑
  （"uid 存的是用户名不是数字，所以按字母序排"）
- **本次扫描的分布** —— 多少行有值、多少个不同值、最常见的几个。
  **实时算，不写死**：写死的数字会随产品变化而说谎。

目录在 `src/model/fields.js`。通用语义与本库观测分开写，不把推断当规范。

### 4.2.2 record 不进列表

`services.record` 里有 29 个键，只有 8 个成列。另外 21 个
（`permission` 113 · `caps` 47 · `apl` 46 · `critical` 21 · `socket` 20 …）
**只在运行单元详情页展开**——一行摊二十几格反而什么都看不清。

### 4.3 "混装"是一等公民

实测**混装的运行单元共 13 个**：10 / 104 个 SA 宿主（`foundation` 一个进程里 **10 个部件、16 个 SA**），
另有 3 / 28 个驱动宿主（`power_host` · `location_host` · `audio_host`）。
这直接决定"改动影响面 / 崩溃定位 / 内存归因"。

改表格后它不能退化成一列里的几个数字，所以：标题那句话**可点成筛选**（一键只看这 13 个）、
混装列用 `⚠ N` 徽标而不是裸数字、类型列保留按实体着色的标签。

### 4.4 筛选与排序

| 控件 | 取值 | 对应数据 |
| --- | --- | --- |
| 类型 | 全部 / SA 宿主 / 驱动宿主 / 守护进程 | `services.type` |
| 排序 | 内容多优先（默认）/ 混装优先 / 名称 / 有问题优先 | 派生 |
| 部件 | 多选 | 内容所属部件的并集 |
| 分区 | system / vendor / updater … | cfg 所在分区 |

## 5. 实体档案页

所有路径的终点，**一个通用模板**，不为每种实体各写页面。

```
┌───────────────────────────────────────────────────────────────┐
│ accessibility                              [部件 · barrierfree]│
│ 仓 barrierfree_accessibility · foundation/.../bundle.json      │
├───────────────────────────────────────────────────────────────┤
│ 🔨 构建   对外接口 7 · syscap 2 · feature 3                    │
│          依赖 23 个部件 · 被 12 个依赖        [展开依赖邻域]   │
│ 📦 镜像   12 个文件：system(10) vendor(2)     [在镜像视图查看] │
│ ▶️ 运行   服务 1 · SA 1(801) · 进程 accessibility [在运行视图] │
├───────────────────────────────────────────────────────────────┤
│ 属性     name / subsystem / manifest / repo …                  │
├───────────────────────────────────────────────────────────────┤
│ 关联     ▸ 对外接口 (7)  ▸ 安装模块 (12)  ▸ 服务 (1)           │
│          ▸ SA (1)        ▸ syscap (2)     ▸ feature (3)        │
├───────────────────────────────────────────────────────────────┤
│ 问题 0                     ▶ 原始声明 record                   │
└───────────────────────────────────────────────────────────────┘
```

**三镜头摘要条**是档案页的核心：一个实体的三种身份并列一屏，各带"跳到对应视角"。
不存在于某镜头的实体（repo 没有运行形态）该行灰显"—"。这一条与首页概念图（§3.2）**互为印证**。

**依赖邻域**：以当前部件为中心的 **1 跳**有向图。实测全图 382 节点 / 5913 边 / 平均出度 15.5，
`hilog` 入度 260 —— 全图必然毛球，**只做 1 跳**；入度 > 50 的热点
（hilog · c_utils · ipc · bounds_checking_function · init · samgr）展开时默认折叠反向边。

## 7. 构建视图与镜像视图（概要）

两者结构与运行视图同构，细化留待各自实施阶段。

**🔨 构建视图**：子系统分面（56 个，`thirdparty` 110 个部件、24 个子系统只有 1 个——
大的可折叠、小的合并为"其它"）→ 部件卡片 → 档案页。

**📦 镜像视图**：路径树（334 个目录、最大深度 6、76% 集中在 2~3 层，非常适合树导航）。
每个文件标注"谁装的 / 属于哪个部件"。`TreePanel` 组件改造复用。

## 8. 质量与治理（过程性）

**定位**：这些是**当前扫描暴露出的不一致**，会随治理逐步收敛，因此**不放首页**，
单独一页，顶栏次级入口。

两类，区别必须写在页面上——这是本页最容易被误解的地方：

| | 含义 | 后果 |
| --- | --- | --- |
| **扫描层**（`advisory = 0`） | 数据本身没读全、没读懂 | 本次扫描被标记 degraded，**先解决它们再信其余的数字** |
| **数据一致性**（`advisory = 1`） | 读到了，但声明之间互相矛盾 | 扫描有明确取舍规则，结论可信；这些是**产品的现状** |

rk3568 实测：扫描层 13 条（`LIBRARY_UNMATCHED` 11、`MANIFEST_JSON` 1、
`ORIGIN_UNMATCHED` 1），数据一致性 151 条，共 15 个问题码。

### 8.1 版式：列表 + 侧边抽屉

```
┌────────────────────────────────┬──────────────────────┐
```

详情走**侧边抽屉**而不是展开在列表下方：上列表下详情的版式，点到第三条
就得把前两条的位置重新找一遍。与镜像/构建视图的叶子抽屉共用
`components/SideDrawer.vue`。

### 8.2 每条问题码都要能被看懂

列表上给**人话标题**（`LIBRARY_UNMATCHED` → "驱动的 so 在镜像里找不到"），
抽屉里给三段：

- **这是什么** —— 扫描器具体看到了什么
- **为什么要管** —— 对使用者的影响；若扫描有取舍规则，写明**谁为准**
- **怎么处理** —— 谁该做什么，以及什么情况下其实无需处理

解释表在 `src/model/issues.js`，逐条对着采集器源码写，不靠码名猜。
末尾有一层按词尾的兜底（`*_UNMATCHED` / `*_AMBIGUOUS` / `*_DIFFERS` …），
新采集器带来的新码不会变成一片空白，只是解释更泛，并标注"按码名归类给出"。

### 8.3 三点要求

1. **可收敛**：每条显示当前数，**为将来多次扫描的趋势对比预留位置**（`↓ 比上次 -12`）。
2. **可分派**：每条能定位到部件与仓，部件名可点进档案。
3. **实例要带 details**：`unresolved=nfc`、`bundle=musl part_name=build_framework`
   这类具体值才是动手的依据；只给 path 和 pointer 等于让人再查一遍。
4. **清单与视图解耦**：治理完成后条目归零，页面自然变空——
   **这是预期行为，不是 bug**。

## 10. URL 与状态

沿用 hash 路由与"URL 即状态"（刷新可恢复、可分享）：

| URL | 页面 |
| --- | --- |
| `#/` | 首页（系统介绍） |
| `#/runtime` | 运行视图（`?kind=&sort=&component=&partition=`） |
| `#/build` | 构建视图（`?subsystem=&q=`） |
| `#/image` | 镜像视图（`?path=system/lib`） |
| `#/e/<table>/<id>` | 实体档案页（**所有实体统一一条路由**） |
| `#/lookup?q=` | 反查结果 |
| `#/findings` · `#/findings/<id>` | 质量与治理 |
| `#/data` · `#/data/<table>` · `#/data/sql` · `#/data/schema` | 数据调测 |

**`?scan=` 始终作为全局参数**出现在每条 URL 上，即使当前库只有 1 次扫描——
将来加版本对比时，既有链接零改动。

## 11. 扩展性：新增采集器时 viewer 不改核心代码

scanner 做到了"放进 `collectors/` 目录即生效"，viewer 应当对称：
**新增一个域，viewer 零核心改动即可用，只是显示不够漂亮。**

靠三样库里现成的元数据：

| 自动发现 | 来源 | 得到什么 |
| --- | --- | --- |
| 本次扫描有哪些域 | `collector_runs.collector` | §9 的表清单、各视角的可用性 |
| 表有哪些列、什么类型 | `PRAGMA table_info` | 表格列、JSON 列解码规则 |
| **表之间怎么关联** | `PRAGMA foreign_key_list` | **档案页"关联"区，双向，全自动** |

外键图实测已完整存在于库中：

```
components                                       → repos
innerapis / syscaps / features / install_modules → components
install_targets / install_module_tags            → install_modules
services                                         → components, install_modules
sas / hdis                        → components, install_modules, services
```

因此档案页"关联"区**不需要为任何域写代码**：正向跟本表 FK 走，反向扫描指向本表的 FK。

唯一手写的是**显示清单**，一个域约 8 行：

```js
// src/model/entities.js —— 新增域只改这里
services: {
  label: '服务', icon: '⚙', colour: 'service',
  title:    r => r.name || r.cfg,     // 卡片 / 档案页标题
  subtitle: r => r.cfg,
  lenses:   ['runtime'],              // 出现在哪些视角
  facets:   ['type', 'component_id'], // 可筛选维度
}
```

**没有清单条目的表也能工作**：在 §9 数据调测里看得到、档案页用通用模板（标题取主键、关联靠 FK），
只是没有图标、不进任何视角、不上首页概念图。这是刻意保留的降级路径，
保证"先能用、再好看"，也让 §9 成为新采集器的默认落脚点。

## 13.1 实施中与本文不同的两处

1. **反查不是"命中即停"**，而是把所有命中的类别按证据强度**全部列出**。
   `accessibility` 同时是服务名和部件名，只给一种会让人以为另一种不存在。
2. **镜像树不做虚拟滚动**，改为每个目录先铺 100 条 + "还有 N 个"。
