# 详情页是否都能用侧边栏承载：评估

日期：2026-10-19
版本：1.0
状态：**评估**。结论的前三条已随本轮一并实施，§5 的两条是建议，未动代码。

---

## 1. 结论

**能，而且已经这么做了。** 本轮把 `openEntity` 改成一律浮抽屉，
取消了原先按外键入边数分流（叶子抽屉 / 枢纽整页）的规则。

真正的理由不是"抽屉够用"，而是**分流本身的代价被低估了**：

- 同一个列表里点不同的列会得到不同的形态，"什么时候浮、什么时候跳"
  变成使用者要背的东西
- 换页丢掉筛选、排序、页码、滚动位置的代价，对枢纽和叶子**是一样的**——
  当初认为"枢纽是要继续往下走的所以该换页"，可继续往下走在抽屉里同样成立，
  抽屉内点关联实体就是换一下抽屉内容
- 分流规则要靠文档解释（`url-spec` §4 写了整整一节），而统一规则不需要

`/e/<table>/<id>` 整页保留，但降级为**两个具体用途**：深链接的落地页，
以及抽屉右上角「在新页面打开 ↗」的去处。不再是任何交互的默认。

---

## 2. 逐个核对：哪些详情现在在哪

| 详情 | 现在 | 能否全进抽屉 |
| --- | --- | --- |
| 七种实体档案（`EntityDossier`） | 抽屉；`/e/…` 作深链接 | **已是** |
| 质量页的问题说明 | 抽屉 | **已是** |
| 列表行详情（六个列表） | 抽屉 | **已是** |
| 运行单元 `/runtime/unit/:id` | 整页 | 能，但**不建议**，见 §4 |
| 镜像视图的文件 | 抽屉 | 已是 |
| 首页 / 反查结果 | 本身不是详情 | — |

抽屉能承载档案的全部内容，这一点已经验证过：`EntityDossier` 的
`compact` 模式把属性表从两列改成一列、隐藏外键列名，460 px 够用；
真放不下的（上万字符的 `record`）本来就是折叠的。

---

## 3. 抽屉作为唯一详情形态，需要守住的四条

这四条都已实现，列在这里是因为**少任何一条，统一形态就会变成退步**：

1. **URL 驱动**。`?detail=<table>/<id>` 决定了它可分享、刷新还在、后退键能关。
   Pinia 驱动的抽屉（v2 的 `DetailSidebar`）三样都没有，那种抽屉确实不该当主力。
2. **能升级成整页**。「在新页面打开 ↗」是打印、贴长链接、并排对比时的出口。
   （实现上有个坑：这个链接不能同时调 `close()`——两个导航会互相抢，
   实测 `close` 的 `replace` 会把跳转吃掉。）
3. **列表保持可用**。不加遮罩、不锁焦点，左边照样能点下一行。
4. **点外面就关**。抽屉盖住右边小半屏，看完不关会一直挡着。
   例外是点列表的另一行——那一下该换内容而不是先关掉。

---

## 4. 唯一不建议进抽屉的：运行单元页

`/runtime/unit/:id` 不是通用档案，它是**另一种讲法**：按部件分组列出装载的
SA / 设备，把"混装"这件事讲清楚。它和 `/e/services/:id`（通用档案）**是同一个
实体的两种呈现**。

现在的问题不是"它该不该进抽屉"，而是**它和 `/e/services/:id` 重复了**：

- 从系统服务列表点一行 → 抽屉（`EntityDossier`）→「在新页面打开」→ `/e/services/:id`
- 从 SA 列表点宿主进程 → `/runtime/unit/:id`

同一个 service 有两个整页地址，内容大半重叠。这是本轮改造暴露出来的，
不是新引入的。

建议（**未实施**）：把运行单元页的"按部件分组的装载清单"并进
`EntityDossier` 对 `services` 的呈现，然后 `/runtime/unit/:id` 重定向到
`/e/services/:id`。这样详情形态与地址都只剩一套。

没有顺手做掉的原因：它要改 `EntityDossier` 的分域呈现逻辑，
而本轮的改动面已经不小；分开做更容易验收。

## 5. 还需要留意的两处

### 5.1 抽屉宽度对宽内容偏窄

安装目标的 `dest`、安装模块的 `label` 都是上百字符，在 460 px 里要折行。
当前靠「超量内容」的展开全文兜住，可用但不舒服。

可选：按实体类型给不同宽度（档案 460 / 问题说明 520 已经这么做了），
或让宽度可拖拽并记在 `localStorage`。建议先不做——没有证据说明这是痛点。

> 2026-10-19 补：内容已按两列表格重排（`FieldTable.vue`），
> 460 px 下的信息密度比原先高一倍多，这一条的紧迫性下降了。

### 5.2 深链接直接打开 `?detail=` 时，背后是空列表

`#/files/targets?detail=install_targets/4210` 直接打开是对的（列表 + 抽屉）。
但 `#/?detail=sas/1` 这种（首页 + 抽屉）在语义上说不通，只是不会报错。
目前没有地方会生成这种链接，不处理；真要处理就在 `DetailDrawer` 里
对"当前路由不是列表"的情况重定向到 `/e/…`。

## 6. 实施记录（本轮已做）

- `openEntity` 一律抽屉，删掉 `isLeaf` 与按入边数分流的逻辑
- 表格主列去掉自带链接：整行点击就是看详情，一行里不该有两种点击行为
  （单元格内的链接加 `.stop`，否则行点击与单元格点击会各发一次 `push`，
  后者覆盖前者——`tools/nav.mjs` 抓到的）
- 列表取消行展开（`type="expand"`），详情统一走抽屉
- 抽屉点外部自动关闭，列表行与抽屉内弹层是例外
- `url-spec.md` §4 的"叶子浮抽屉、枢纽换整页"需随之改写
