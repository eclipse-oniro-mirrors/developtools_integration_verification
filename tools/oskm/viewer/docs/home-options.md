# 首页优化：可选方案

日期：2026-10-19
版本：1.1
状态：**已实施**（方案丁 + §4 两件）。

针对"结合当前的目录结构，让首页展示内容更直观"。
全部结论基于对 `Home.vue` 与 `knowledge.db` 的实测，测量方法见 §6。

---

## 1. 现状有四个问题，都是可测的

### P1 首页和顶栏在讲两套词

顶栏（上一轮改造后）是**三组七视图**：运行时进程 / 部件信息 / 系统文件。
首页讲的仍是**三种读法**：构建视图 / 镜像视图 / 运行视图。

同一个产品，两套名字、两种分法。新人先在首页学会"三种读法"，
抬头看顶栏发现没有这三个词——首页最重要的教学作用因此落空。

### P2 概念模型 7 个节点，5 个点进去落错地方

实测（点击每个节点记录落点）：

| 节点 | 实际去向 | 应该去 |
| --- | --- | --- |
| 仓 repo | `/parts/components` | **`/parts/repos`** |
| 部件 component | `/parts/components` | ✓ |
| 安装模块 install_module | `/files/image` | **`/files/targets`** |
| 安装目标 install_target | `/files/image` | **`/files/targets`** |
| 服务 service | `/runtime/services` | ✓ |
| SA | `/runtime/services` | **`/runtime/sa`** |
| HDI 设备 | `/runtime/services` | **`/runtime/hdi`** |

点"仓 525"落到部件列表、点"SA 165"落到服务列表。
这是上一轮新增四个视图时漏改的，不是设计问题——但它说明
**首页的入口和实际视图是两套各自维护的东西**，还会再错。

### P3 真正的入口在首屏之外

首页内容高 **1316 px**，视口 848 px。首屏放得下"它是什么"+概念模型+三读法；
"你可以用它做什么"那四张入口卡要滚动才看得见。

### P4 "这些数字能不能信"被埋在页脚

本次扫描 **6 个采集器有 3 个是 `degraded`**（components / hdi / services），
扫描层问题 13 条。这直接决定上面那些数字的可信度，
现在却是页脚一行小字里的几个 `✓ ! ✕`。

另外 "你可以用它做什么" 的四张卡中有三张与三读法重复，同一件事说了两遍。

## 2. 一个关键观察：导航三组 **就是** 概念模型三段

这是本次方案的支点。现有的概念模型是一条链：

```
仓 → 部件 → 安装模块 → 安装目标 → 服务 → SA / HDI
```

而顶栏的三组，恰好是这条链的三段：

| 顶栏分组 | 链上的位置 | 二级视图 |
| --- | --- | --- |
| **部件信息** | 源码侧 | 代码仓 525 · 部件 382 |
| **系统文件** | 镜像侧 | 安装目标 5,804（含安装模块 5,501）· 镜像视图 |
| **运行时进程** | 运行侧 | 系统服务 164 · SA 服务 165 · HDI 服务 57 |

**不是巧合**：目录结构本来就是按"源码 → 镜像 → 运行"分的。

所以概念模型图和导航**可以是同一张图**——这同时解掉 P1（只剩一套词）
和 P2（节点即入口，不会再各自维护成两套）。

## 3. 四个方案

### 方案甲：原地修补

修五个错链接、把"三种读法"的文案换成三组的名字，其余不动。

- **优点**：半小时的事，风险为零
- **缺点**：P3、P4 一个没解决；首页仍然是"先教学再给入口"的顺序，
  而回头客（每天用的人）要的是入口
- **定位**：如果只想先止血，做这个

### 方案乙：仪表盘

砍掉概念模型，首屏换成三组大卡，每组列二级入口与数字，顶部一条扫描状态带。

- **优点**：首屏即入口，与导航 1:1；P1–P4 全解
- **缺点**：**丢掉教学价值**。`ux-design` §1 把"首页讲清系统是什么"
  列为首页的核心目的，仪表盘回答不了"仓、部件、安装模块之间什么关系"
- **定位**：如果使用者已经都是熟手，这个最高效

### 方案丙：左右两栏（模型 + 入口并置）

左边保留概念模型图，右边三组入口卡。

- **优点**：教学与入口都在首屏
- **缺点**：仍然是两套表述并排放着，P1 没真正解决，只是把矛盾摆到了一起；
  1280 px 以下两栏会挤
- **定位**：折中，但折得不彻底

### 方案丁：让概念模型**成为**导航（推荐）

把纵向的链横过来，按三组切成三段。**每个节点就是一个二级视图的入口**，
节点上的数字就是该视图的行数。

```
┌─ 部件信息 ──────────┐   构建安装   ┌─ 系统文件 ─────────┐   init 拉起   ┌─ 运行时进程 ────────┐
│  代码仓        525  │ ───────────▶ │  安装模块    5,501 │ ────────────▶ │  系统服务      164 │
│  部件          382  │              │  安装目标    5,804 │               │  SA 服务       165 │
│   对外接口 1,743    │              │   8 个分区         │               │  HDI 服务       57 │
│   syscap 306       │              │  镜像视图（按路径） │               │   其中 13 个混装 ⚠ │
└────────────────────┘              └───────────────────┘               └───────────────────┘
          314/525 个仓有部件参与构建        5,804 个文件来自 5,501 个模块       1 个进程 / 11 个驱动归属未知
```

- **一张图既是数据模型也是导航**：点哪个方块就进哪个视图，不可能再对不上
- **词汇只剩一套**：图上的分组名就是顶栏的分组名
- **箭头承载关系**："部件 ——构建安装——→ 文件 ——init 拉起——→ 进程"，
  这正是现在要靠三段文字解释的东西
- 每段底下一行小字放该段的**特征数字**（归属未知、混装），
  把"这次扫描有什么特别"带进首屏
- 窄屏退化为纵向，就是今天的样子，不需要第二套布局

**代价**：1600 px 下三段各约 460 px，放得下；1280 px 会紧，需要让第三段的
子项换行。需要实测确认。

## 4. 另外两件，与方案选择无关，建议都做

### 4.1 扫描可信度提到首屏

现在"3/6 个采集器 degraded、13 条扫描层问题"在页脚。建议做成
hero 下方一条状态带：

```
rk3568 · 扫描 #1 · 2026-10-18 12:18     6 个采集器：3 完整 · 3 degraded     扫描层问题 13 →
```

degraded 时整条带警示色。理由写在 `issues.js` 里了：
**扫描层问题要先解决，再信其余的数字**——那么它就该出现在数字旁边，
而不是数字下面滚两屏的地方。

### 4.2 反查入口在首页给一个实体位置

反查是测试集成人员的主入口（`ux-design` 的既定目标读者），
现在首页只在"能做什么"卡片里提了一句，而那张卡在首屏之外。
建议 hero 下方直接给一个输入框（与顶栏 ⌘K 同源），
带一行真实例子：`libaccessibleabilityms.z.so → accessibility (barrierfree)`。

**方案丁 + §4 两件。** 分两步：

| 步 | 内容 | 量 |

| **一** | 修五个错链接（P2）——不论最终选哪个方案都要做 | ~10 行 |

回归建议加进 `tools/nav.mjs`：**首页每个节点点进去的落点必须等于它标注的视图**
（这次的 5 个错链接，有这条断言就不会发生）；以及首屏高度 ≤ 视口 + 20%。

## 6. 测量方法

- **链接落点**：playwright 逐个点击 `.node`，记录 `location.hash`，与期望比对
- **首屏高度**：`document.querySelector('.home').scrollHeight` 对比视口
- **扫描状态**：`collector_runs` 的 `status` 分布；`issues` 按 `advisory` 分组
- **特征数字**：对 `services` / `hdis` / `install_modules` 统计 `component_id IS NULL`；
  混装取 `components` 去重数 > 1 的运行单元
