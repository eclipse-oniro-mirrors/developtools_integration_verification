## 1. 现状测量

| | 实测 |
| --- | --- |
| 整页档案内容宽 | **940 px**（`.page` 写死 `max-width: 940px`） |

也就是说：**整页只是"更宽的抽屉"**，宽出来的 820 px 什么也没放。

## 2. 抽屉与整页本就不该一样

它们服务的动作不同：

| | 抽屉 | 整页 |
| --- | --- | --- |
| 从哪来 | 列表里点一行 | 深链接、「在新页面打开」 |
| 旁边有什么 | 左边是列表，还要继续点下一行 | 没有别的，这一页就是全部 |
| 典型动作 | **扫一眼就走** | **读完、对照、复制、打印** |
| 约束 | 宽 460，不能挡住列表 | 宽度随窗口，没有别的东西要让位 |

所以抽屉应当**纵向单栏、默认折起次要区块**；整页应当**横向铺开、默认全展开**。
现在两者共用一套纵向单栏，等于让整页迁就抽屉。

## 3. 部件详情页的三个具体问题

拿 `hilog`（`/e/components/204`）做样本：

### P1 最该看的"产出什么"被压成折叠计数

关联区是五行：`feature 2 / 对外接口 8 / 安装模块 13 / 服务 2 / syscap 1`，
每一行都要点开才看得到内容。而"这个部件产出了什么"正是打开部件档案的首要问题。

### P2 同一组数字说了两遍

三镜头对部件给的是：

```
构建   对外接口 8 · syscap 1 · feature 2
镜像   13 个安装模块
运行   服务 2
```

和关联区的五行**完全是同一批数字**。三镜头对其它实体有用（它回答"这个 SA 属于哪个
部件、由谁装入"），但对部件自己，它只是把关联区又数了一遍。

### P3 属性区没有分组，原始字段与关键字段平级

实测字段顺序：`部件名 · 子系统 · 部件清单 · deps · feature · syscap ·
adapted_system_type · build · ram · rom`。

其中 `deps` 是 1140 字符的 JSON，`build` / `ram` / `rom` /
`adapted_system_type` 是 bundle.json 的原始声明，和"部件名""子系统"平级排列。
列目录（`columns/components.js`）里本来就有分组（身份 / 依赖 / 产出），
但档案页没有用——它按 `PRAGMA table_info` 的物理列序排。

## 4. 布局方案（已实施）

**整页：头部通栏 + 下面两栏。**

```
┌─────────────────────────────────────────────────────────┐
│ 面包屑                                                   │
│ 图标  名称                                      类型标签 │
│ 三镜头（通栏，一行三格）                                 │
├───────────────────────────────┬─────────────────────────┤
│ 属性                          │ 关联                    │
│   两列字段表                  │   反向关联默认展开       │
│ 其它声明                      │                         │
│   两列字段表                  │                         │
├───────────────────────────────┴─────────────────────────┤
│ 原始声明 record（通栏，默认折起）                        │
└─────────────────────────────────────────────────────────┘
```

- 左栏 1.3fr、右栏 1fr，`min-width: 1180px` 才分栏，窄了自动回到单栏
- **不设 `max-width`**，宽度随窗口；靠两栏切分避免单行过长
- 抽屉（`compact`）不受影响，仍是纵向单栏

实现用 CSS Grid 的 `grid-template-areas`，区块缺席（如没有"其它声明"）
不会留空洞。抽屉与整页仍是同一个组件、同一份内容，只是布局规则不同——
不要为整页另写一套模板，那必然会两边长歪。

## 5. 部件专项（已实施，见 §7）

### 方案甲：按列目录的分组重排属性区

档案页的属性顺序改为跟随 `columns/*.js` 的 `group`（身份 / 依赖 / 产出 …），
没有登记的列归到末尾的"其它"。

- 解 P3，通用——六张有列目录的表都受益
- 约 30 行

### 方案乙：关联区对"反向关联"默认展开前几条

把 `对外接口 8 条` 这种折叠计数，改成默认列出前 5 条 + "还有 3 条"。

- 解 P1，通用
- 整页空间够，抽屉里可以仍然折叠
- 约 25 行

### 方案丙：三镜头对"自己就是该域主角"的实体不显示

部件在构建域本来就是主角，再给它一个"构建：对外接口 8 · syscap 1"等于自指。
规则：**当镜头指向的就是实体自己所属的域时，不渲染该镜头**。

- 解 P2
- 需要给每个实体登记"主域"（`entities.js` 加一个字段，约 8 行）

**建议三个都做**，它们各自独立、都通用，不是部件专属的补丁。
合计约 70 行。

### 不建议做的

- **给部件写一套专门的档案模板**。那会开一个坏头：七种实体迟早各写一套，
  `EntityDossier` 的通用性就没了。上面三条都是通用改进，正好反过来。

## 7. 实施记录（2026-10-19）

§5 的三项都做了，但**方案丙换了实现方式**，比原设想更简单。

### 7.1 甲：属性按列目录分组

`columns/index.js` 加 `groupsOf(table)`，`EntityDossier` 按它给属性区分段，
`FieldTable` 渲染分组表头行。没有登记的列归到末尾的"其它"。

部件档案的属性区从「部件名 · 子系统 · 部件清单 · deps · feature · syscap · …」
平铺，变成 **身份 / 依赖 / 产出** 三段。

顺带查出一个**错配**：列目录里的 `features` / `syscaps` 描述的是"关联行的计数"
（列表视图里那一列），而库里的 `features` / `syscap` 列装的是 bundle.json 的
**原始 JSON 数组**——名字撞了，含义不是一回事。于是档案页把计数的说明挂到了
数组上。处理：给 components 的三个原始列（`deps` / `features` / `syscap`）
单独写条目，并把查找顺序改成 **本表的 EXTRA 优先于列目录**。

### 7.2 乙：反向关联默认露出条目

不再是「对外接口 8 条」一行折叠计数，而是直接列出前几条（抽屉 3 条、整页 6 条），
超出的给「还有 N 条，展开看」。"这个部件产出了什么"正是打开部件档案的首要问题，
把答案折起来再要求点开是没道理的。

### 7.3 丙：改用更简单的判据，不需要给实体登记"主域"

原方案是给每个实体登记一个"主域"，当镜头指向自己的域时不渲染。
实现时发现有个更直接的判据：**镜头有没有指向别的实体**。

- 部件的三行（`对外接口 8 · syscap 1` / `13 个安装模块` / `服务 2`）
  全都只是反向关联的计数，没有跳转目标 → 全部隐藏，整块不出现
- SA 的三行分别指向它的部件、安装模块、宿主进程 → 全部保留

一行 `l.to || l.unit` 就够，不必新增 `entities.js` 字段。
三镜头的定位也因此更清楚了：**它回答"这个实体在另外两个域里对应的是谁"**，
纯计数交给关联区。

### 7.4 回归里两条写死了旧行为

- `smoke.mjs` 的「部件档案有三镜头」断言的正是本轮刻意去掉的东西，
  改为断言"按分组列属性"，另加一条"SA 仍保留三镜头"守住边界
- `table.mjs` 的「属性是两列表格」取第一行，而第一行现在是分组表头
  （只有跨列 th、没有 td）——限定 `tr:not(.gh)`

另外我自己写测试时又踩一次：用 `/^syscap/` 判断"裸列名"，结果
"syscap 声明"也被命中，断言假失败。要匹配裸名就得精确比对。

`tools/table.mjs` 扩到 70 条。
