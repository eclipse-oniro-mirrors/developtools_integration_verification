# 部件详情页重设计方案（3 个选项）

## 背景

当前部件详情页用的是通用 `EntityDossier.vue` 模板——所有实体（部件/服务/SA/安装目标…）共用一套
属性表 + 关联区 + 原始声明。这个模板的优点是统一，缺点是对部件这种信息维度丰富的实体，
用户要在一堆属性里自己分辨"这是 InnerAPI 计数""那是原始 syscap 数组"——字段含义不直观。

目标：为部件单独设计一个 Tab 式详情页，**每个 Tab 聚焦一个维度**，每条信息都带解释。

## 可用数据

部件一行（`components` 表 + `record` JSON）及其关联表：

| 维度 | 数据来源 | 内容 |
|------|----------|------|
| 基本信息 | `components` 列 + `record` | name, subsystem, manifest, repo_id, description, rom, ram, adapted_system_type |
| InnerAPI | `innerapis` 表 (1:N) | name(GN label), external_name(引用名), field(inner_kits/inner_api), install_module_id |
| 特性 | `features` 表 (1:N) | value(特性名), gn_arg_id(关联编译参数) |
| SysCap | `syscaps` 表 (1:N) | value(SystemCapability.X.Y.Z) |
| 编译参数 | `gn_args` 表 (0:N, decl_file 前缀匹配) | name, current_value, default_value, value_type, has_override, decl_file, decl_line, comment |
| 依赖关系 | `deps` JSON + 反向计算 | deps.components(正向), dependents(反向), deps.third_party(三方库) |
| 安装产物 | `install_modules` + `install_targets` (1:N) | label, type, source, dest, size, symlink |
| 运行时 | `services` + `sas` + `hdis` (1:N) | 服务名/cfg, SA ID/libpath, HDI 设备名/library |
| 构建声明 | `record.build` | module_list, inner_kits, inner_api, test_list, conditions, group_type |

## 公共头部（三个方案共用）

无论哪个方案，页面顶部固定一个头部区域：

```
┌─────────────────────────────────────────────────────────────┐
│ [build icon] bundle_framework                    [部件 · 编译参数]
│              bundlemanager / bundle_framework                  │
│              manifest: foundation/bundlemanager/bundle.json   │
└─────────────────────────────────────────────────────────────┘
```

- 部件名（mono 字体，最大字号）
- 子系统 / 代码仓名（次要色）
- manifest 路径（mono，可点击跳转）
- 右侧标签：实体类型
- 不再显示三镜头（部件的三镜头是自述计数，已确认信息量低）

---

## 方案 A：6-Tab 按维度平铺

每个维度一个 Tab，信息粒度最细，切换成本适中。

```
┌──────────────────────────────────────────────────────────────────┐
│ [头部]                                                            │
├────────┬────────┬──────┬────────┬────────┬──────────────────────┤
│基本信息│InnerAPI│ 特性  │SysCap  │编译参数 │     依赖与产物       │
├────────┴────────┴──────┴────────┴────────┴──────────────────────┤
│                                                                  │
│  当前 Tab 内容                                                    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 各 Tab 内容

**Tab 1 · 基本信息**

| 字段 | 值 | 含义 |
|------|-----|------|
| 部件名 | `bundle_framework` | 构建与归属的基本单位，改动影响面以它为准。取自构建索引键，不是 bundle.json 里的 `component.name`。 |
| 子系统 | `bundlemanager` | 部件所属的子系统。取自构建索引，与 bundle.json 不一致时记 `SUBSYSTEM_DIFFERS`。 |
| 代码仓 | `bundle_framework` | 部件代码所在的 git 仓，按 manifest 路径最长前缀匹配。可点击跳转。 |
| 部件清单 | `foundation/bundlemanager/bundle.json` | 声明这个部件的文件，扫描器读的就是它。 |
| 描述 | `text` | bundle.json 里 `component.description` 的自由文本。 |
| ROM | `12KB` | 镜像占用，来自 `component.rom`。 |
| RAM | `3MB` | 运行内存占用，来自 `component.ram`。 |
| 适配系统类型 | `["standard"]` | 支持的系统类型，来自 `component.adapted_system_type`。 |
| 构建目标数 | 15 | `record.build.module_list` 数组长度，装进镜像的构建目标数。 |
| 测试目标数 | 8 | `record.build.test_list` 数组长度。 |

字段以键值对形式排列，每行右侧有 ⓘ 说明。

**Tab 2 · InnerAPI**

表格 + 每列有 ⓘ 列头说明：

| GN label ⓘ | 引用名 ⓘ | 类型 ⓘ | 安装模块 ⓘ | 序号 |
|-------------|----------|--------|-----------|------|
| `//foundation/...:bundle_mgr` | `bundle_framework:bundle_mgr` | inner_kits | libbundle_mgr.z.so | 0 |

列头 ⓘ：
- **GN label**：inner_kits/inner_api 中声明的 GN target label。其他部件通过 external_deps 引用这个 label 来使用接口。
- **引用名**：external_deps 中使用的引用名（component:target 格式）。不是所有 innerapi 都有 external_name。
- **类型**：声明来源。inner_kits 是传统接口声明，inner_api 是新的统一接口声明方式。
- **安装模块**：component_links 按 label 名匹配到的安装模块。为空表示没找到同名模块。

空表时显示："这个部件没有声明对外接口"。

**Tab 3 · 特性**

| 特性名 ⓘ | 关联编译参数 ⓘ | 序号 |
|----------|--------------|------|
| `a_flag` | ✓ 已关联 → `a_flag` | 0 |

列头 ⓘ：
- **特性名**：bundle.json 中 `component.features` 数组的一项。特性名通常与 gn_args.name 相同，对应一个 GN declare_args() 编译参数。
- **关联编译参数**：component_links 按 features.value ↔ gn_args.name 匹配的结果。为空表示没找到同名的编译参数。

**Tab 4 · SysCap**

| 能力名 ⓘ | 序号 |
|----------|------|
| `SystemCapability.BundleManager.BundleFramework` | 0 |

列头 ⓘ：
- **能力名**：格式为 SystemCapability.X.Y.Z，声明这个部件提供了什么系统能力。设备根据 SysCap 列表判断一个产品是否支持某项能力。

**Tab 5 · 编译参数**

| 参数名 ⓘ | 当前值 ⓘ | 默认值 ⓘ | 类型 ⓘ | 覆盖 ⓘ | 声明文件 ⓘ | 行号 | 注释 |
|----------|----------|---------|--------|--------|----------|------|------|
| `a_flag` | `true` | `false` | bool | ✓ | `foundation/.../bundle.gni` | 42 | Enable feature A |

列头 ⓘ：
- **参数名**：GN declare_args() 中声明的构建参数名。由 `gn args --list --json` 输出，全局唯一。
- **当前值**：该参数在当前产品构建中生效的值。有产品覆盖取覆盖值，否则取默认值。
- **默认值**：declare_args() 中声明的默认值。未被产品覆盖时此值即为生效值。
- **类型**：值的类型 bool/str/int/list，从 GN 字面量解析得出。
- **覆盖**：✓ 表示 args.gn 中显式设置了该参数的值。
- **声明文件**：声明该参数的 .gni 或 BUILD.gn 文件路径。

**Tab 6 · 依赖与产物**

分为三个区块（非 Tab，是同一页内的折叠区段）：

- **依赖关系**
  - 依赖了谁：`deps.components` 列表，每项可点击跳转到对应部件。标红不存在的部件。
  - 被谁依赖：反向计算列表，每项可点击跳转。
  - 三方库依赖：`deps.third_party` 列表。
- **安装产物**：install_modules 表格（label, type, source），可展开看 install_targets（dest, size, symlink）。
- **运行时**：services / sas / hdis 三个子表格，每行可点击跳转。

### 优缺点

- ✅ 每个维度独立，用户可以直接跳到关心的 Tab
- ✅ InnerAPI/特性/SysCap/编译参数各有专属空间，解释充分
- ❌ 6 个 Tab，窄屏时 Tab 栏可能换行
- ❌ 依赖与产物混在一起，信息密度高

## 方案 B：4-Tab 按用途分组

把相关维度合并，减少 Tab 数量，每个 Tab 内用子标题区分。

```
┌──────────────────────────────────────────────────────────────────┐
│ [头部]                                                            │
├──────────┬──────────┬──────────────┬─────────────────────────────┤
│  概览     │ 对外声明  │ 编译参数与依赖 │       安装与运行           │
├──────────┴──────────┴──────────────┴─────────────────────────────┤
│                                                                  │
│  当前 Tab 内容                                                    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 各 Tab 内容

**Tab 1 · 概览**

基本信息（同方案 A 的 Tab 1）+ 维度计数卡片：

```
┌─────────────────────────────────────────┐
│ 基本信息                                  │
│  部件名   bundle_framework                │
│  子系统   bundlemanager                   │
│  代码仓   bundle_framework                │
│  ...                                     │
├─────────────────────────────────────────┤
│ 维度概览                                  │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐    │
│  │InnerAPI│ │ 特性 │ │SysCap│ │编译参数│    │
│  │   8   │ │   3  │ │  1   │ │   12  │    │
│  └──────┘ └──────┘ └──────┘ └──────┘    │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐    │
│  │被依赖 │ │依赖  │ │安装  │ │服务  │    │
│  │  15  │ │  4   │ │  3   │ │  2   │    │
│  └──────┘ └──────┘ └──────┘ └──────┘    │
└─────────────────────────────────────────┘
```

计数卡片可点击跳到对应 Tab。

**Tab 2 · 对外声明**

三个子区块，各有小标题和解释：

```
─── InnerAPI（8 条）──────────────────────────
  这个部件给别的部件用的接口。
  [表格：GN label / 引用名 / 类型 / 安装模块]
  ⚠ 空时："没有声明对外接口"

─── 特性（3 条）─────────────────────────────
  可配置开关名，通常与编译参数同名。
  [表格：特性名 / 关联编译参数]

─── SysCap（1 条）────────────────────────────
  声明提供的系统能力，设备据此判断产品是否支持。
  [表格：能力名]
```

**Tab 3 · 编译参数与依赖**

```
─── 编译参数（12 个，3 个被覆盖）─────────────────
  GN declare_args() 声明在这个部件源码目录里的参数。
  [表格：参数名 / 当前值 / 默认值 / 类型 / 覆盖 / 声明文件]

─── 依赖关系 ────────────────────────────────
  依赖了谁（4 个）  → [部件列表，可点击]
  被谁依赖（15 个） → [部件列表，可点击]
  三方库依赖（2 个）→ [库名列表]
```

**Tab 4 · 安装与运行**

```
─── 安装模块（3 个）─────────────────────────
  装进镜像的构建目标。
  [表格：label / type / source]
  └ 展开看安装目标（dest / size / symlink）

─── 系统服务（2 个）─────────────────────────
  init 配置声明的服务。
  [表格：服务名 / cfg / 进程名]

─── SA 服务（5 个）──────────────────────────
  [表格：SA ID / libpath / profile]

─── HDI 设备（1 个）─────────────────────────
  [表格：设备名 / library / node]
```

### 优缺点

- ✅ 4 个 Tab，导航清晰，窄屏也友好
- ✅ 概览页给全局印象，计数卡片可跳转
- ✅ 相关维度合并在一个 Tab 内，上下文连贯
- ❌ 对外声明 Tab 里三个子区块混在一起，不如独立 Tab 专注
- ❌ 编译参数与依赖放一起，两者关联不大

---

## 方案 C：5-Tab 平衡（推荐）

在 A 的细分和 B 的聚合之间取平衡。

```
┌──────────────────────────────────────────────────────────────────┐
│ [头部]                                                            │
├────────┬──────────┬────────┬────────┬───────────────────────────┤
│基本信息│ 对外声明   │编译参数 │依赖关系 │       安装与运行          │
├────────┴──────────┴────────┴────────┴───────────────────────────┤
│                                                                  │
│  当前 Tab 内容                                                    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 各 Tab 内容

**Tab 1 · 基本信息**

同方案 A，但底部加一行维度计数摘要（不是卡片，是一行文字）：

```
InnerAPI 8 · 特性 3 · SysCap 1 · 编译参数 12 · 被依赖 15 · 安装模块 3
```

每项可点击跳到对应 Tab。

**Tab 2 · 对外声明**

同方案 B 的 Tab 2：InnerAPI + 特性 + SysCap 三个子区块。

但与方案 B 不同的是——编译参数独立成 Tab，依赖关系独立成 Tab，
所以这个 Tab 只装"声明性"内容，不混入配置和依赖。

**Tab 3 · 编译参数**

同方案 A 的 Tab 5，独立空间，表格 + 列头 ⓘ 解释。

**Tab 4 · 依赖关系**

```
─── 依赖了谁（4 个）────────────────────────────
  这个部件运行/构建需要哪些部件。
  [列表：部件名 → 可点击跳转，不存在的标红]

─── 被谁依赖（15 个）───────────────────────────
  改动这个部件会影响哪些部件。
  [列表：部件名 → 可点击跳转]

─── 三方库依赖（2 个）─────────────────────────
  [列表：库名]
```

**Tab 5 · 安装与运行**

同方案 B 的 Tab 4：安装模块 + 服务 + SA + HDI。

### 优缺点

- ✅ 5 个 Tab，既不太多也不太少
- ✅ 编译参数和依赖关系各自独立，解释空间充足
- ✅ 对外声明合并在一个 Tab，因为 InnerAPI/特性/SysCap 本质都是"部件声明自己提供什么"
- ✅ 基本信息底的维度计数摘要可快速跳转
- ❌ 对外声明 Tab 仍有三个子区块（但比方案 B 少了一个编译参数的干扰）

---

## 对比

| 维度 | 方案 A (6-Tab) | 方案 B (4-Tab) | 方案 C (5-Tab) |
|------|---------------|---------------|---------------|
| Tab 数 | 6 | 4 | 5 |
| 每个维度独立 Tab | InnerAPI/特性/SysCap 各自独立 | 合并为对外声明 | 合并为对外声明 |
| 编译参数 | 独立 Tab | 与依赖合并 | 独立 Tab |
| 依赖关系 | 与产物合并 | 与编译参数合并 | 独立 Tab |
| 概览/计数卡片 | 无 | 有（Tab 1） | 有（信息底摘要行） |
| 窄屏友好 | 一般 | 好 | 较好 |
| 信息密度 | 每 Tab 低 | 每 Tab 高 | 中等 |
| 解释充分度 | 最高 | 中等 | 高 |

## 待确认

1. **Tab 顺序**：当前建议 基本信息 → 对外声明 → 编译参数 → 依赖关系 → 安装与运行。
   是否需要调整？（例如把依赖关系放在编译参数前面？）

2. **空内容处理**：某个 Tab 没有数据时（比如部件没有 InnerAPI），
   是显示空表格 + "没有声明对外接口"，还是在 Tab 栏标注 "(0)" 或灰掉 Tab？

3. **跳转交互**：表格里的可点击项（InnerAPI 关联的安装模块、依赖的部件等），
   点击后是打开侧边抽屉（当前模式），还是在当前页面内跳转？

4. **Tab 持久化**：选中的 Tab 是否写入 URL（`?tab=innerapi`），
   以便复制链接时对方直接看到同一个 Tab？
