# 运行视图改表格：可行性评估

日期：2026-10-19
版本：1.1
状态：**已实施**，实施记录与实测代价见 §9。§5 的选型结论被用户决策推翻，原文保留。

针对："把运行时页面转换为列表方式呈现，把各个统计信息都列进来，并提供点击展示下钻。
同时提供按任意列排序、过滤、搜索、导出等功能。给每个列使用更好理解的词语，
提供在线字段详情解释说明，让信息展示更充分。"

结论先行：**该转，而且收益比预期大**——但不要复用调测面那套 el-table，
理由在 §5。全部结论基于对 `knowledge.db` 与现有代码的实测，测量方法见 §8。

> **后续**：用户选择了甲（el-table，"不要造轮子"），并决定 record 字段不进列表。
> §5 对代价的估计偏低了——真实代价不是包体而是渲染耗时，见 §9.2。

## 1. 这批数据适不适合表格

适合，而且现在的卡片已经装不下了。

| | 实测 |
| --- | --- |
| 行数 | **164** 个运行单元 |
| 已成列的字段 | **14** 个（name / cfg / type / executable / uid / gid / start_mode / ondemand / secon / sandbox / importance / component / subsystem / install_label） |
| 只在 `record` 里、没有列的字段 | **21** 个 |
| 卡片当前展示的事实 | **6** 个 |

164 行、十几个属性、需要横向比较——这是表格的典型形状。
卡片适合"少量对象、每个都要讲个故事"，而这里是"一百多个同构对象、要找出哪个不一样"。

### 1.1 最大的发现：一多半的事实现在根本没露出来

`services.record` 里有 **29 个键，只有 8 个有同名列**。只存在于 `record` 里的 21 个中，
恰恰有测试集成最关心的那些：

| 字段 | 出现 | 是什么 |
| --- | ---: | --- |
| `path` | 163 | 可执行文件与参数的原始声明 |
| `permission` | 113 | 该进程申请的权限 |
| `permission_acls` | 59 | 需要 ACL 的权限 |
| `caps` | 47 | Linux capabilities |
| `apl` | 46 | APL 等级 |
| `jobs` | 35 | 绑定的 init job |
| `critical` | 21 | 崩溃重启策略 |
| `socket` | 20 | 预建 socket |
| `writepid` | 15 | pid 写到哪 |
| `bootevents` | 12 | 启动事件 |
| `setuid` / `disabled` / `once` / `cgroup` / `console` / `kernel_permission` / … | ≤ 11 | |

**这些不需要改扫描器就能用**——`record` 本来就是"原始全集，列只是为性能做的投影"
（见 `docs/architecture` 的 record 原则）。viewer 直接读 `record` 即可。

所以"让信息展示更充分"不是把现有 6 个事实排成一行，而是**从 6 个变成 20+ 个**。
这一条单独就足以支持改表格。

## 2. 四项功能各自的代价与坑

### 2.1 按任意列排序 —— 不能一律当字符串比

实测的存储类型很不规整，这是最容易写错的地方：

| 字段 | 看起来 | 实际 | 排序要怎么处理 |
| --- | --- | --- | --- |
| `uid` | 数字 | **TEXT，存的是名字**（`root`、`access_token`） | 按名字排，不是数值 |
| `gid` | 数字 | **TEXT，存的是 JSON 数组**（`["root","shell",…]`） | 按个数或首项排，得明说 |
| `ondemand` | 布尔 | `integer` 80 行 / `null` 84 行 | **三态** |
| `sandbox` | 布尔 | `0` 35 行 / `null` 129 行 | 三态，且 `0` 与"未声明"是两回事 |
| `importance` | 数字 | `-20` 24 行 / `null` 140 行 | 三态 |
| `apl` | 字符串 | 45 行字符串 + **1 行数组** | 渲染要兜住异构 |
| `bootevents` | 数组 | 9 行数组 + **3 行字符串** | 同上 |

**`null` 与 `0` 必须区分显示。** `sandbox = 0`（显式关闭）和"没声明"是完全不同的事实，
表格里一律渲染成空白就把信息抹掉了。建议：未声明显示 `—`，`0` 就显示 `0`。

排序还要定义 `null` 排在哪（建议恒定排末尾，升降序都是——这样"有声明的"永远先看到）。

### 2.2 过滤与搜索 —— 已有一半

现有的 `kind` / `part` 两个筛选已经在 URL 里了（`useQueryState`）。
要补的是：按列的值筛（type / subsystem / 有无 issue / 是否混装）、全文搜索。

164 行全在内存，纯前端做；实测切换筛选 **65 ms**（预算 100），加几个条件不会有问题。
**新增的筛选条件都应当进 URL**，与 `url-spec.md` §1 已定的规矩一致。

### 2.3 导出 —— 语义要先说清楚

两个必须先定的问题，定错了用户会投诉数据不对：

1. **导出什么范围**：全集 164 行，还是当前筛选结果？
   建议**当前筛选 + 当前可见列**，并在文件名里带上条件（`runtime-hdf-28行.csv`），
   这是唯一不会让人困惑的语义。
2. **CSV 公式注入**：以 `=` `+` `-` `@` 开头的单元格，Excel 会当公式执行。
   当前库里**实测 0 处**，但 `importance = -20` 这类值随时可能变成字符串形态。
   加一行前缀转义的成本接近零，值得直接做。

格式：CSV（给 Excel）+ JSON（给脚本）。纯前端 Blob 下载，无需服务端。

### 2.4 列名人话 + 在线字段解释 —— 有现成的模式可抄

刚做完的 `src/model/issues.js` 就是这个模式：一张常量目录表，
配合表头上的 ⓘ 点出解释。照搬成 `src/model/fields.js`。

每个字段写三样：

- **列名**：`secon` → "SELinux 安全上下文"，`apl` → "APL 权限等级"
- **是什么**：字段的含义
- **本库里的分布**：如"162 条有值、2 条未声明；153 个不同值"

第三样很重要，而且必须写成**从数据算出来、不是写死的**——
它既能帮使用者判断这列有没有筛选价值，又不会随产品变化而说谎。
（`sandbox` 35 条里全是 `0`、`importance` 24 条里全是 `-20`，
知道这件事就不会浪费时间去按它排序。）

**诚实边界**：字段的通用语义（init 的约定）与"这个库里观察到什么"是两类陈述，
目录里要分开写，不能把推断当成规范。

## 3. 下钻怎么做

两级，刚好对应两种意图：

| 动作 | 结果 | 为什么 |
| --- | --- | --- |
| 点行上的 ▸ | **就地展开**，列出装载的 SA / 设备 | 102 个单元只装 1 个、29 个装 ≥2 个（最多 16 个）。想看一眼不值得换页 |
| 点名字 | 进 `#/runtime/<id>` 整页 | `services` 外键入边 2，是**枢纽**——按 `url-spec.md` §4 的既定规则走整页 |

注意不要用侧边抽屉：抽屉是给**叶子**的，而运行单元是枢纽，
规则已经定了就别破例，否则"什么时候浮什么时候跳"又变成要背的东西。

## 4. 会失去什么

卡片现在传达一件表格天然不擅长的事：**13 个运行单元装载了多个部件的内容**——
这是整个运行视图想让人看见的那个结论，卡片用一个醒目徽标把它顶出来。

表格里它会退化成一列里的若干个标记。补偿办法：

1. 表头上方的那句话保留（现在就有："其中 13 个装载了多个部件的内容——改动影响面与崩溃定位都卡在这里"），
   并做成**可点的筛选**，一键只看这 13 个。
2. 行首保留按类型着色的左边条（SA / 驱动 / 守护进程），类型信息不靠读字。
3. "混装"列用徽标而不是数字，保持视觉重量。

做到这三条，损失可以接受。

## 5. 实现路径：三选一

### 甲：复用调测面的 `el-table`

- **优点**：排序、列宽、固定列全都现成，工作量最小
- **代价**：`TableView` 这个 chunk 是 **122 KB JS + 35 KB CSS（gzip 41.6 + 5.1）**，
  目前只在进入 `/data/*` 时才加载。搬到产品面意味着 `#/runtime` 首包多 **~47 KB gzip**
- **更要命的是观感**：产品面与调测面是**刻意区隔**的两个面
  （`implementation-plan` §4：调测面"更密、带横幅，让离开产品界面成为可见信号"）。
  运行视图长成 el-table 的样子，这条区隔就糊了
- 另外三态渲染、`PathChip`、徽标、带 ⓘ 的表头都得自定义单元格，
  省下来的其实没有看上去那么多

### 乙：自写轻量表格（推荐）

- 164 行**不需要虚拟滚动**（镜像视图 5804 行的树都没用，分批渲染就够）
- 需要的就三件：sticky 表头、点表头排序、列显隐。约 **300 行**
- 单元格本来就要自定义，自写反而更直接
- 零新增依赖，产品面首包不变，设计语言保持一致

### 丙：卡片 / 表格双视图切换

- **不推荐**。两套代码路径、两套回归，而且多数人不会发现还有另一个视图。
  §4 的三条补偿做到位，卡片就没有保留的必要了。

## 6. 推荐方案

**乙 + §4 的三条补偿 + 两级下钻。** 分三步，各自可独立验收：

| 步 | 内容 | 量 |
| --- | --- | --- |
| **一** | `components/DataTable.vue` 轻量表格（sticky 表头、任意列排序、列显隐、行展开）+ 运行视图接上，列仍用现有 14 个字段 | ~380 行 |
| **二** | `model/fields.js` 字段目录：人话列名 + ⓘ 解释 + 实时分布；接入 `record` 里那 21 个字段 | ~200 行 |
| **三** | 过滤条（按列筛 + 全文搜索，全部进 URL）+ 导出 CSV/JSON | ~160 行 |

配套回归进 `tools/nav.mjs`：排序正确（含三态 null 恒定排末尾）、筛选进 URL、
列显隐进 URL、展开不跳页、导出内容与当前筛选一致、ⓘ 能打开且有内容。

性能上要守住的两条现有预算：`#/runtime` 首屏 3000 ms（现 630 ms）、
切换筛选 100 ms（现 65 ms）。DOM 节点会从 2232 涨到约 164 × 20 ≈ 3300，
仍远低于镜像视图的量级。

### 不建议一起做的

- **分页**。164 行一次铺完比翻页快，也便于 Ctrl-F。将来真上到几千行再说。
- **列宽拖拽**。成本不低、收益很小，列显隐已经解决了"看不下"的问题。
- **保存视图预设**。URL 已经能分享，等真有人抱怨再说。

## 8. 测量方法

- **字段与类型**：`PRAGMA table_info(services)`；`typeof(col)` 逐列统计；
  `record` 逐行 `json.loads` 后统计键频次与值类型
- **包体**：`npm run build` 的 chunk 清单
- **性能**：`npm run perf`（首页 LCP、各视图含 8.9 MB db 的可交互时间、筛选切换）
- **CSV 注入面**：扫描 `record` 中所有字符串值，统计以 `=` `+` `-` `@` 开头的数量

## 9. 实施记录（2026-10-19）

用户决策，与 §6 的推荐有一处反转：

| | 评估推荐 | 实际采纳 |
| --- | --- | --- |
| 表格实现 | 乙 自写轻量表格 | **甲 el-table**（"不要造轮子"） |
| record 字段 | 接入列表 | **不进列表，只在详情页展开** |
| 字段解释深度 | 甲（通用语义 + 本库分布） | 甲 |

### 9.1 做了什么

- `src/model/fields.js`：19 列目录。人话列名、三段说明（含义 / 在 oskm 里怎么来的 /
  本次扫描的分布），分布由 `distribution()` 实时算。排序 `sortRows()` 保证三态列的
  "未声明"恒定排末尾。
- `src/model/export.js`：CSV（带 BOM、公式注入转义）+ JSON，范围是当前筛选 × 当前可见列。
- `Runtime.vue` 改 el-table：任意列排序、列显隐、搜索、筛选、行展开、导出，全部状态进 URL。
- `RuntimeUnit.vue` 增"其它声明"段，展开 record 里那 21 个没有成列的键。

### 9.2 el-table 的代价：实测，不是估计

把卡片换成 el-table，**筛选切换从 65 ms 涨到约 420–490 ms**（164 行 × 9 列重建）。
逐项 A/B 过，结论是优化不了：

| 改动 | 164 行耗时 |
| --- | ---: |
| 基线（9 列） | 489 / 473 ms |
| 去掉 `show-overflow-tooltip` | 455 / 439 ms |
| 去掉 `PathChip` | 460 / 477 ms |
| 去掉固定列 | 443 / 426 ms |
| 去掉展开列 | 378 / 371 ms |
| **整个单元格模板塌成一个纯插值** | **420 / 419 ms** |

最后一行是决定性的：把自定义渲染全部拿掉仍要 420 ms，
说明开销在 el-table 自身的每行机制里，自定义单元格只占 12%。

能真正解决的只有两条，都要砍掉已承诺的功能：

- **el-table-v2 虚拟滚动**：展开行只支持树形数据，装不下"展开看装载的 SA 清单"这种自定义面板
- **分页**：164 行一次铺完才能 Ctrl-F 全表，分页是倒退

所以 `tools/perf.mjs` 的"运行视图切换筛选"预算从 100 ms 调到 600 ms，
并在代码里写明这是**有代价的取舍而不是迁就实现**，以及将来行数上千时回来重新权衡。
换来的是十几列可排序 / 可筛选 / 可导出的信息密度。

首屏时间从 630 ms 涨到 1412 ms（预算 3000），DOM 从 2232 涨到 5916 节点。

### 9.3 实施中查出来的

- **展开列必须也 `fixed="left"`**。进程名是固定列会被提到固定层，
  不固定的展开列就落到它右边，箭头和名字对不上。
- **至少要有一列用 `min-width`**，否则窗口宽时右边留一条空白。
- **表头多了 ⓘ 之后窄列会换行**，几个数字列都要加宽十几像素。
- **`text-transform: uppercase` 把产品名 `oskm` 改成了 `OSKM`。**
  那行标题全是中文，大写转换对中文毫无作用，只把唯一的英文词改错了。
- **我的三态排序测试第一版是假阳性**：用「沙箱」测，而它的有值行全是 `0`，
  升序降序看起来一模一样，根本没验到方向。换成有 是/否 两种取值的「按需启动」才测得出。

`tools/table.mjs` 24 条回归并入 `npm run verify`（现八项）。
