# oskm Viewer UX 备选方案

日期：2026-10-18；状态：**备选方案，待选型**。面向读者：需要快速看懂一个 OpenHarmony 产品架构的系统开发人员。
本文所有数据特征均来自 `viewer/knowledge.db`（rk3568）实测。

## 1. 现有设计的问题

`ux-design.md` v2 的组织方式是**一个数据库表一个 tab**：

```
概览 · repos · components · services · sas · hdis · modules · issues
```

然后是列表 → 详情 → 再跳到另一个列表的过滤视图。这是一个做得不错的**通用数据库浏览器**，
但它有四个结构性问题：

**① 要求读者先懂 schema。** "这个进程里跑了哪些 SA"这个问题，在当前设计里要先知道
SA 表有 `process` 列，再去 `#/sas?process=xxx`。而开发者脑子里的入口是"进程"，不是"sas 表"。

**② 数据里真实存在的结构被打平了。** 下面第 2 节会看到，这套数据里至少有三种彼此正交的结构，
每一种都是开发者熟悉的心智模型。当前设计把它们全部降维成"表 + 外键跳转"，
每一步只能看到一跳，走三跳才能拼出一条链，**而拼接发生在读者脑子里**。

**③ 量级不可见。** 5501 个 install_modules 和 57 个 HDI 在导航栏上是同样大的两个 tab。
一个产品"重在哪里"是架构理解的第一步，表格给不了。

**④ 与通用工具同质。** Datasette / sqlite-web 已经把"浏览 SQLite 表"做到很好了。
再实现一遍，oskm 独有的价值（跨域关联已经解析好）一点没用上。

一句话：**当前设计把"数据怎么存"呈现给了用户，而不是"系统长什么样"。**

## 2. 数据里真实存在的三种结构（实测）

| 结构 | 形态 | 规模 | 适合什么导航 |
| --- | --- | --- | --- |
| **构建/归属** | repo → component → innerapi / syscap / feature | 525 / 382 / 1743·306·1351 | 分面 + 依赖 ego 图 |
| **镜像/文件** | partition → 目录 → 文件 → 安装模块 → 部件 | 8 / 334 目录 / 5804 文件，最大深度 6 | **路径树**（层级浅、分支均匀） |
| **运行/进程** | 进程 → service(cfg) → SA / HDI → 库 | 104 SA 进程 + 27 HDI host；164 service（sa 104 / hdf 28 / default 31） | 进程卡片列表 |

同一个部件在三种结构里都出现，但扮演的角色不同。**能在三个镜头之间来回切换，正是"看懂架构"的过程。**

几个决定可视化可行性的硬数据：

- **部件依赖图：382 节点 / 5913 条有效边，平均出度 15.5，`hilog` 入度 260。**
  → 全图必然是毛球，**图谱只能做 ego 网络（1 跳邻域），不能做总览**。
- **子系统分布极不均匀**：`thirdparty` 110 个部件，而 24 个子系统只有 1 个部件。
  → 按子系统分层的树会一边倒，需要"大的可折叠、小的合并"。
- **镜像路径树：334 个目录、最大深度 6、2~3 层占 76%。** → 树导航非常合适。
- **没有文件体积数据**（`install_targets` 不存 size）。→ treemap 只能按**数量**定面积，说服力打折。
- **10 / 104 个 SA 进程混装了多个部件的 SA**，`foundation` 一个进程里有 **10 个不同部件**。
  → 这是表格永远显示不出来、但对系统开发者极有价值的事实。
- **部件产物跨分区**：245 个部件只落 1 个分区，78 个落 2 个，16 个落 3~4 个。

## 3. 五个备选方案

### 方案 A：实体档案页为中心（Dossier）

**隐喻**：每个实体一张"档案"，像 GitHub 的仓库首页。没有表 tab，只有一个搜索框和实体页。

```
┌───────────────────────────────────────────────────────────┐
│ 🔍 搜索任意名称 / 路径 / label                             │
├───────────────────────────────────────────────────────────┤
│ accessibility                        [部件 · barrierfree] │
│ 仓 barrierfree_accessibility · 清单 .../bundle.json        │
├───────────────────────────────────────────────────────────┤
│ 构建   对外接口 7 · syscap 2 · feature 3                   │
│        被 12 个部件依赖 · 依赖 23 个部件        [展开邻域] │
│ 镜像   12 个文件 → system(10) vendor(2)         [看目录]  │
│ 运行   1 个服务 accessibility · 1 个 SA(801) · 进程 同名   │
├───────────────────────────────────────────────────────────┤
│ 问题  0                                                    │
└───────────────────────────────────────────────────────────┘
```

| | |
| --- | --- |
| 优点 | "我有一个名字，告诉我关于它的一切"——最常见的入口；零 schema 知识；三种结构在同一页并列，关系天然可见 |
| 缺点 | **没有发现性**：不知道要搜什么就无从下手；"列出所有 X"做不了 |
| 成本 | 中（1 个页面模板 × 6 种实体 + 搜索） |
| 失效点 | 新人第一次打开不知道从哪开始 |

### 方案 B：三视角切换（Three Lenses）

**隐喻**：同一个系统的三张地图。顶层不是表，是**视角**。

```
[ 构建视图 ]  [ 镜像视图 ]  [ 运行视图 ]        ← 顶层只有三个
```

每个视角是**为那个心智模型专门做的导航**，而不是通用表格：

- **运行视图**：进程卡片列表（131 个），点开 = 这个进程由哪个 cfg 拉起、里面有哪些 SA/HDI、
  这些东西分别属于哪几个部件。
- **构建视图**：子系统 → 部件分面，部件页带 1 跳依赖 ego 图。
- **镜像视图**：`system/ vendor/ updater/…` 路径树，每个文件标注"谁装的 / 属于哪个部件"。

选中一个实体后，可以**在另外两个视角里定位它**（"在镜像视图中查看"）。

| | |
| --- | --- |
| 优点 | 三个视角本身就是架构知识；切换动作强制读者建立"同一个东西的三种身份"；每个视角都能独立回答一类问题 |
| 缺点 | 要做三套导航 UI；有的实体不在所有视角里（repo 没有运行形态） |
| 成本 | 高（三套导航 + 一个跨视角定位机制） |
| 失效点 | 如果三个视角做得太像（都退化成表格），就白做了 |

### 方案 C：问题驱动首页（Question-first）

**隐喻**：首页不是数据，是**一串问题**。点一个问题，进一个为它定制的答案页。

```
进程与启动
  · 开机后有哪些进程？分别由谁拉起？
  · 哪些进程混装了多个部件的 SA？            ← 实测 10 个
  · 哪些 SA 声明了但没有对应的实现库？        ← 实测 4 个
部件与接口
  · 哪些部件声明了对外接口却没有安装产物？    ← 实测 484 条
  · 构建标成 platformsdk 但部件没声明的库？   ← 实测 258 个
  · 谁依赖 hilog？（入度最高的 6 个部件）
镜像
  · system/lib 下 3330 个库分别属于谁？
  · 哪些部件的产物跨了多个分区？              ← 实测 94 个
质量
  · 13 个扫描层问题 · 151 条 advisory
[ 自由查询 ▸ ]
```

| | |
| --- | --- |
| 优点 | 直接服务"直观理解"；首页本身就是**这套数据能回答什么**的说明书；每个答案页可以用最合适的呈现（表/图/树），不必统一 |
| 缺点 | 问题集是封闭的，必须配一个逃生口（自由查询）；问题清单需要持续维护 |
| 成本 | 低起步（先做 5 个问题），可增量 |
| 失效点 | 问题选得不对就变成摆设——需要先问真实用户 |

### 方案 D：地图优先（Map / Treemap）

**隐喻**：先看全貌比例，再钻取。首屏是一张按数量定面积的分区图。

| | |
| --- | --- |
| 优点 | 唯一能一屏回答"这个产品重在哪里"的形式 |
| 缺点 | **没有体积数据**，只能按文件数/模块数定面积，而"文件数多"≠"重要"，说服力明显弱于按字节；`thirdparty` 110 个部件会吃掉大半画布 |
| 成本 | 中（treemap 布局 + 钻取） |
| 结论 | **不建议作为主结构**。若将来 scanner 增加 `install_targets.size`，它会立刻变成最强的首屏 |

### 方案 E：图谱优先（Graph）

**隐喻**：首屏是部件依赖力导向图。

| | |
| --- | --- |
| 优点 | 依赖关系是架构的核心，图最直观 |
| 缺点 | **实测 382 节点 / 5913 边 / 平均度 15.5**，力导向必然是毛球；`hilog` 入度 260，会把图拽成一个黑洞 |
| 成本 | 中高 |
| 结论 | **不建议作为主结构**；但"以某部件为中心的 1 跳邻域"非常有用，应当作为档案页里的一个面板 |

## 4. 推荐：B 为骨架，A 为交汇点，C 为入口

三者不是三选一，而是**三个不同层级**，组合起来刚好覆盖"不知道找什么 → 知道找什么 → 找到了要看全"：

```
首页 = 问题清单（C）        ← 不知道从哪开始的人，从这里获得第一个认知
   ↓ 点进任一问题
三视角之一（B）             ← 在"运行/构建/镜像"中的一个里导航
   ↓ 点中一个实体
实体档案页（A）             ← 三种身份汇合，含依赖 ego 图（E 降级为面板）
   ↓ "在镜像视图中查看"
回到另一个视角（B）
```

D 与 E 降级为**档案页内的面板**，不做主结构（理由见上，都是数据特征决定的）。

### 4.1 运行视图首屏草图（最值得先做的一屏）

```
┌─────────────────────────────────────────────────────────────────────┐
│ 运行视图 · 131 个进程            [全部] [SA 进程 104] [HDI host 27] │
├─────────────────────────────────────────────────────────────────────┤
│ ⬢ foundation                                      10 个部件 ⚠ 混装  │
│   由 system/etc/init/foundation.cfg 拉起                             │
│   SA ×24   bundle_framework · window_manager · ability_runtime · …  │
├─────────────────────────────────────────────────────────────────────┤
│ ⬢ accessibility                                            1 个部件 │
│   由 system/etc/init/accessibility.cfg 拉起                          │
│   SA ×1    accessibility(801)                                        │
├─────────────────────────────────────────────────────────────────────┤
│ ⬡ usb_host                                      HDI host · 1 个部件 │
│   由 vendor/etc/init/hdf_devhost.cfg 拉起（-n usb_host）             │
│   设备 ×3  drivers_peripheral_usb                                    │
└─────────────────────────────────────────────────────────────────────┘
```

"⚠ 混装"这个标记在当前表格设计里是看不到的，而它恰恰是系统开发者最关心的事实之一。

### 4.2 一个必须处理的数据细节

`sas.process` / `hdis.process` 是 **JSON 列**，取出来是 `"foundation"`（带引号）而不是 `foundation`。
viewer 里任何按进程分组/展示的地方都要先解码，否则界面上会出现带引号的进程名。

## 5. 怎么低成本验证选型

不要先写代码。按这个顺序花半天：

1. **挑 5 个真实问题**，找 2~3 个系统开发者确认这些问题是不是他们真会问的（方案 C 的问题清单就是候选）。
2. 用 **SQL 直接把答案查出来**贴给他们看，观察他们接下来会问什么——**追问的方向就是导航该去的方向**。
3. 只为"运行视图首屏"（§4.1）做一张静态 HTML，不接数据库。确认这一屏是否比现在的 `#/sas` 表格更有用。
4. 确认后再决定是否推翻 `url-spec.md` 的路由设计。

| `url-spec.md` 的 8 个表路由 | **降级**为"自由查询/逃生口"，不再是主导航 |
| `ux-design.md` v2 的 tab 导航与分页表格 | **替换** |

## 7. 待确认

1. 主结构选 **B+A+C 组合**，还是单独某一个？
2. 运行视图是否值得作为第一个实现的视角（我的判断：是，因为它信息密度最高且现在最缺）？
3. scanner 要不要补 `install_targets.size`？补了之后方案 D 会从"不建议"变成"很强"。
4. 目标读者是只有系统开发者，还是也包括测试/集成人员？后者会显著改变问题清单（方案 C）。
