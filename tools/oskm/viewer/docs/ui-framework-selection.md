# oskm Viewer UI 框架选型报告

日期：2026-10-18  
状态：**调研报告**，待决策。

## 1. 现状分析

当前 viewer 是纯 vanilla JS + 手写 CSS，616 行 JS + 215 行 CSS + 85 行 HTML。

### 1.1 已有的功能复杂度

| 维度 | 当前状态 | 问题 |
|------|---------|------|
| JS 函数数 | 33 个 | 偏多，但每个职责单一 |
| 内联 HTML 模板 | 113 个标签字符串拼接 | **主要痛点**：HTML 在 JS 里用字符串拼，无可维护性 |
| onclick= 内联事件 | 24 处 | 全局函数耦合，无法组件化 |
| CSS | 215 行手写 | 已有暗色主题+响应式，但无设计系统 |
| 数据查询 | sql.js 直接调 | 不需要框架改变 |
| 构建 | 无 | 零构建步骤，直接打开 HTML |

### 1.2 即将增加的复杂度

- 关系图（SVG 可视化）
- Scan 对比视图
- 表格排序/列配置
- 更多实体类型的详情模板
- 搜索结果分类展示

这些功能用 vanilla JS 可以实现，但模板拼接和状态管理会越来越难维护。

## 2. 候选方案

### 方案 A：保持 Vanilla JS + 引入轻量模板引擎

| 维度 | 评价 |
|------|------|
| 选型 | lit-html（3KB）或 htm（1KB）替代字符串拼接 |
| 优点 | 零构建、最小依赖、渐进式引入 |
| 缺点 | 无组件化、无状态管理、仍需手写大量 DOM 操作 |
| 适合 | 如果功能不再大幅扩展 |

### 方案 B：Preact + htm（无构建步骤）

| 维度 | 评价 |
|------|------|
| 选型 | Preact（3KB）+ htm（1KB），用模板字符串写 JSX |
| 优点 | 组件化、虚拟 DOM diff、状态管理（hooks）、CDN 直引无需构建 |
| 缺点 | 需要学习 hooks；htm 语法不如真 JSX 友好 |
| 构建步骤 | 无（CDN 直引或本地 vendor） |
| 适合 | 中等复杂度单页应用 |

### 方案 C：Vue 3 + CDN（无构建步骤）

| 维度 | 评价 |
|------|------|
| 选型 | Vue 3 Global Build（~40KB gzip），CDN 直引 |
| 优点 | 模板语法直观（HTML 里写模板）、响应式数据绑定、单文件组件 |
| 缺点 | 包体积较大；全局 build 无 Tree-shaking |
| 构建步骤 | 无 |
| 适合 | 模板多、交互复杂、团队熟悉 Vue |

### 方案 D：Svelte + 构建步骤

| 维度 | 评价 |
|------|------|
| 选型 | Svelte 5 + Vite |
| 优点 | 编译时框架，运行时最小；语法简洁；内置状态管理 |
| 缺点 | 需要构建步骤（Vite）；增加 node_modules 依赖 |
| 构建步骤 | 需要 |
| 适合 | 追求最优性能和最小运行时 |

### 方案 E：Lit + Web Components

| 维度 | 评价 |
|------|------|
| 选型 | Lit（5KB），Web Components 标准 |
| 优点 | 标准化组件、Shadow DOM 封装、可跨框架复用 |
| 缺点 | Web Components API 较底层；Shadow DOM 样式隔离可能与主题冲突 |
| 构建步骤 | 可选（CDN 或 Vite） |
| 适合 | 长期可复用的组件库 |

### 方案 F：Alpine.js（零构建）

| 维度 | 评价 |
|------|------|
| 选型 | Alpine.js 3（~15KB gzip），CDN 直引 |
| 优点 | 在 HTML 里写交互逻辑（类似 Vue 但更轻量）、零构建、学习成本极低 |
| 缺点 | 无虚拟 DOM，大数据列表性能不如 Preact/Vue；组件复用能力弱 |
| 构建步骤 | 无 |
| 适合 | 以模板为主、逻辑较少的场景 |

## 3. 评估矩阵

| 维度 | A: Vanilla+lit-html | B: Preact+htm | C: Vue3 CDN | D: Svelte+Vite | E: Lit | F: Alpine.js |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| **包体积** | ~4KB | ~4KB | ~40KB | ~2KB | ~5KB | ~15KB |
| **构建步骤** | 无 | 无 | 无 | 需要 | 可选 | 无 |
| **模板能力** | 中 | 高 | 高 | 高 | 中 | 中 |
| **状态管理** | 手写 | hooks | 响应式 | 内置 | 手写 | 响应式 |
| **组件复用** | 弱 | 强 | 强 | 强 | 强 | 弱 |
| **学习成本** | 低 | 中 | 低(会Vue) | 中 | 中 | 极低 |
| **大数据列表** | 好 | 好 | 好 | 最好 | 好 | 一般 |
| **生态/文档** | 少 | 好 | 丰富 | 丰富 | 中 | 中 |
| **与现有代码兼容** | 高 | 中 | 低(重写) | 低(重写) | 中 | 高 |

## 4. 推荐分析

### 4.1 关键约束

1. **无构建步骤优先**：当前 viewer 的核心优势是零配置——打开 HTML 就能用。引入构建步骤会改变分发模型。
2. **sql.js 不变**：数据层与 UI 框架无关，任何框架都能用。
3. **模板驱动**：主要痛点是 113 个内联 HTML 拼接，需要模板化。
4. **移动端响应式**：当前 CSS 已实现，框架不改变这一点。
5. **单文件分发**：最好能用单 HTML + JS + CSS 文件分发。

### 4.2 推荐方案：B（Preact + htm）

**理由**：

1. **无构建步骤**：CDN 或本地 vendor 直引，保持零配置优势。
2. **最小体积**：Preact 3KB + htm 1KB = 4KB，比当前 sql.js WASM（685KB）小两个数量级。
3. **组件化**：把 6 种实体详情拆成 6 个组件，消除 113 个内联 HTML 拼接。
4. **Hooks 状态管理**：`useState` 管理选中实体/当前 tab/分页，替代当前散落的全局变量。
5. **虚拟 DOM**：大数据列表（install_modules 5501 条）diff 性能好于直接 innerHTML。
6. **渐进迁移**：可以先用 Preact 重写详情面板，树和搜索保持 vanilla JS，逐步迁移。

**不选 Vue 3 的原因**：包体积 40KB（10×），全局 build 无法 Tree-shaking，且需要整体重写。

**不选 Svelte 的原因**：需要 Vite 构建，引入 node_modules 依赖，改变分发模型。

**不选 Alpine.js 的原因**：无虚拟 DOM，5501 条 install_modules 列表渲染性能无保障；组件复用能力弱。

### 4.3 迁移路径

| 阶段 | 内容 | 产出 |
|------|------|------|
| 1 | 引入 Preact+htm vendor，重写详情面板 | 6 个实体详情组件，消除内联 HTML |
| 2 | 重写树视图为组件 | 树节点组件，props 驱动展开 |
| 3 | 重写搜索结果 | 搜索组件，分类展示 |
| 4 | 重写关联+Issues | 右栏组件化 |
| 5 | 添加关系图 | SVG 组件（可选 D3 或手写） |

## 5. 备选：保持 Vanilla JS 的条件

如果满足以下全部条件，可以不引入框架：

1. 功能不再扩展（当前 33 个函数足够覆盖所有需求）
2. 模板拼接用 `<template>` 标签或 lit-html 改善
3. 搜索/列表性能可接受（当前 sql.js 分页已解决）
4. 不需要组件复用

**判断**：如果只做关系图和 scan 对比两个新功能，vanilla JS 足够。如果还要加更多视图或团队协作开发，建议引入 Preact。

## 6. 最终建议

| 场景 | 建议 |
|------|------|
| 个人工具、功能稳定 | 保持 Vanilla JS + `<template>` 改善模板 |
| 需要扩展更多视图 | Preact + htm（方案 B） |
| 团队开发、长期维护 | Svelte + Vite（方案 D），接受构建步骤 |

**当前推荐**：Preact + htm（方案 B），在保持零构建优势的同时获得组件化能力。
